# Layer 1: 知识层 (Knowledge Layer)

> UrhoX SCE 平台七层架构分析 — 第一层

---

## 1. 定义

知识层是 AI 辅助开发的 **认知基础设施**，包含引擎运行所需的全部技术文档、示例代码、类型定义和项目模板。它不直接参与代码执行，而是作为 AI 决策层（L6）的唯一知识来源，决定了 AI 产出代码的质量上限。

**核心隐喻**：如果 AI 决策层是大脑，知识层就是大脑的记忆库——记忆的准确性和完整性直接决定了决策的质量。

---

## 2. 设计目标

| 目标 | 说明 |
|------|------|
| **完整性** | 覆盖引擎全部可用 API、已知陷阱、最佳实践 |
| **可检索性** | AI 能够根据任务类型快速定位到相关文档 |
| **准确性** | 文档与实际引擎行为严格一致，无过时信息 |
| **示范性** | 提供可直接复用的代码示例，而非纯 API 签名 |
| **类型安全** | 通过 EmmyLua 类型定义，在编码阶段提供类型检查 |

---

## 3. 组成要素

### 3.1 引擎 API 文档 (engine-docs/)

平台的技术文档体系采用分层组织：

```
engine-docs/
├── principles.md              # 开发准则（必读入口）
├── lua-scripting-guide.md     # Lua 开发指南（必读入口）
├── built-in-models.md         # 内置 3D 模型尺寸参考
├── api/                       # API 参考文档
│   ├── core.md                #   场景/节点/组件
│   ├── graphics.md            #   渲染/模型/精灵
│   ├── physics.md             #   3D 物理
│   ├── Physics2D.md           #   2D 物理 (Box2D)
│   ├── input.md               #   输入处理
│   ├── audio.md               #   音频系统
│   ├── math.md                #   数学工具
│   ├── enums.md               #   枚举值完整列表
│   └── nanovg.md              #   NanoVG 矢量绘图
├── recipes/                   # 解决方案手册
│   ├── ui.md                  #   UI 系统指南

│   ├── materials.md           #   材质系统
│   ├── rendering.md           #   渲染管线
│   ├── json.md                #   JSON 编解码
│   ├── file-storage.md        #   本地存档
│   ├── client-cloud-score.md  #   客户端云变量

    └── camera.md              #   相机相关陷阱（目前唯一文件）
```

### 3.2 示例代码 (examples/)

22 个示例，按复杂度分级：

| 级别 | 符号 | 数量 | 含义 |
|------|------|------|------|
| 入门 | 🌱 | 0 | 最基础用法 |
| 中级 | 🌿 | 14 | 完整功能演示 |
| 高级 | 🌳 | 8 | 完整游戏 / 复杂系统 |

**示例覆盖的游戏类型**：
- 2D 休闲：Flappy Bird、平台跳跃
- 3D 游戏：水果忍者、第三人称射击、Minecraft 体素世界
- UI 系统：Windows 10 模拟器、组件画廊、聊天窗口
- 技术专题：NanoVG 渲染、视频播放、云变量、虚拟列表

**索引机制**：`examples/api-index.md` 提供按 API 维度的交叉索引。

### 3.3 类型定义 (.emmylua/)

EmmyLua 类型声明文件，被 Lua LSP 自动加载，提供：
- 全局 API 类型签名（所有引擎 C++ 绑定的 Lua 接口）
- 177 个事件类型定义（`Events.d.lua`）
- 枚举常量定义

**作用**：在编码阶段通过 LSP 提供类型检查和自动补全，减少运行时错误。

### 3.4 项目模板 (templates/)

4 个标准脚手架：

| 脚手架 | 适用场景 |
|--------|---------|
| `scaffold-2d.lua` | 纯 2D 休闲游戏 |
| `scaffold-2d-physics.lua` | 2D 物理游戏（平台跳跃等） |
| `scaffold-3d-scene.lua` | 3D 场景展示（自由相机） |
| `scaffold-3d-character.lua` | 3D 角色游戏（Fall Guys 风格） |

### 3.5 引擎工具库 (urhox-libs/)

平台级工具库，包含：
- 平台适配（PlatformUtils）
- 输入管理（InputManager）
- UI 组件系统（40+ 控件，Yoga Flexbox 布局）
- 第三人称相机（ThirdPersonCamera）
- UIScaler 缩放适配

## 4. 能力边界

### 能做什么

| 能力 | 具体表现 |
|------|---------|
| API 查询 | 通过文档快速找到任意引擎 API 的签名和用法 |
| 模式匹配 | 根据游戏类型选择最合适的脚手架和示例 |
| 陷阱预警 | 通过已记录的 gotchas 避免已知问题 |
| 类型校验 | 通过 EmmyLua 定义在 LSP 层面捕获类型错误 |
| 代码复用 | 从示例中提取可直接使用的代码片段 |

### 不能做什么

| 限制 | 影响 |
|------|------|
| 无自动更新机制 | 文档可能滞后于引擎实际 API |
| 无版本关联 | 不清楚文档对应哪个引擎版本 |
| 无运行时验证 | 文档正确性无法在运行时校验 |
| 无交互式探索 | 不能像 REPL 一样实时试验 API |
| gotcha 覆盖不足 | 仅 1 个文件 vs 实际 20+ 已知陷阱 |

## 5. 与其他层的关系

### 上游依赖

| 依赖层 | 关系 | 说明 |
|--------|------|------|
| L4 运行时层 | **被描述** | 知识层文档描述运行时层的 API 行为 |

### 下游被依赖

| 依赖层 | 关系 | 说明 |
|--------|------|------|
| L2 规范层 | **被引用** | 规则文档引用知识层的具体 API 文档 |
| L6 AI 决策层 | **被读取** | AI 通过读取知识层文档来做出编码决策 |

### 关键依赖链

```
L4 (Runtime) ──API行为──→ L1 (Knowledge) ──文档映射──→ L6 (AI Decision)
                                ↓
                          L2 (Specification) ←──规则引用
```

**核心风险**：L1 与 L4 的一致性无自动保障。当引擎 API 变更时，文档可能不同步更新，导致 AI 基于过时知识生成错误代码。

## 6. 深度洞察

### 6.1 知识层的三重角色

知识层实际扮演三个角色：

1. **参考手册**（API 文档）—— 回答"这个函数怎么用"
2. **教学材料**（示例代码）—— 回答"这类游戏怎么做"
3. **防错屏障**（gotchas + 类型定义）—— 回答"哪些事不能做"

当前第 1 和第 2 角色比较完善，第 3 角色严重不足。

### 6.2 示例代码的双刃剑效应

22 个示例是平台最有价值的知识资产之一，但存在两个结构性问题：

**问题 A：零入门级示例**
- 🌱（入门）= 0 个，最低门槛是 🌿（中级）
- 对纯新手不够友好，缺少 "Hello World" 级别的最简示例

**问题 B：示例-脚手架二元体系的模糊边界**
- 脚手架是"空壳 + 注释"，示例是"完整实现"
- 中间缺少"脚手架 + 最小实现"的过渡形态
- 开发者常困惑：应该从脚手架开始填充，还是从示例开始修改？

### 6.3 Gotcha 系统的严重缺陷

**现状**：gotchas/ 目录仅有 1 个文件（camera.md）

**散落的 gotchas**：至少 20+ 已知陷阱散布在 4 个不同位置：
- CLAUDE.md Rules 内嵌（如 eventData 访问方式、数组索引）
- lua-scripting-guide.md 的"关键注意事项"
- 各 API 文档的"注意"段落
- 示例代码的注释中

**应有但缺失的 gotchas**（至少 15 个）：
- NanoVG 字体必须在 Start() 中创建
- Box2D 碰撞体必须在同一节点
- SetMode() 已禁用
- eventData 的 tolua++ 绑定特殊性
- Lua 数组从 1 开始
- table.unpack 在构造器中的行为
- 枚举值 vs 数字常量
- orthoSize 的 0.5 因子
- 程序化材质的 Technique 路径
- UI 系统废弃过渡
- 鼠标模式设置
- 3D 模型尺寸获取
- CustomGeometry 用法
- 多人/单机模式判断
- 第三人称相机必须使用库

### 6.4 类型定义的隐性价值

.emmylua/ 的 177 个事件类型定义是一个被低估的资产。它不仅服务 LSP 补全，更是 **事件系统的完整注册表**——理论上可以从中生成事件文档、验证事件订阅正确性，但目前仅用于编辑器补全。

## 7. 风险评估

| 风险 | 等级 | 影响 | 缓解措施 |
|------|------|------|---------|
| 文档与引擎 API 不同步 | 🔴 高 | AI 生成的代码在运行时失败 | 需要文档-API 一致性检查机制 |
| Gotcha 碎片化 | 🔴 高 | 同一陷阱被反复踩中 | 统一 gotcha 系统，从 1→12 文件 |
| 零入门示例 | 🟡 中 | 新手用户上手困难 | 增加 3-5 个 🌱 级别示例 |
| 文档无版本管理 | 🟡 中 | 无法追溯文档变更历史 | 引入文档版本标记 |
| 类型定义不完整 | 🟡 中 | LSP 无法检查所有 API 调用 | 持续完善 .emmylua 定义 |

## 8. 优化建议

### 8.1 统一 Gotcha 系统（P0 优先级）

将散落在 4 个位置的 20+ gotchas 统一到 `engine-docs/gotchas/` 目录：

```
engine-docs/gotchas/
├── index.md              # 速查索引
├── camera.md             # 相机陷阱（已有）
├── nanovg.md             # NanoVG 陷阱（字体、渲染事件）
├── physics2d.md          # Box2D 陷阱（碰撞体位置）
├── input.md              # 输入陷阱（枚举 vs 数字）
├── ui.md                 # UI 陷阱（废弃系统、布局溢出）
├── lua-binding.md        # Lua 绑定陷阱（eventData、数组索引）
├── resolution.md         # 分辨率陷阱（SetMode 禁用）
├── materials.md          # 材质陷阱（Technique 路径）
├── models.md             # 模型陷阱（尺寸获取）
├── multiplayer.md        # 多人游戏陷阱（模式判断）
└── lua-language.md       # Lua 语言陷阱（unpack、索引）
```

**每个 gotcha 文件统一格式**：
```markdown
## [GOTCHA-ID] 简短标题
- **症状**: 用户看到什么现象
- **原因**: 为什么会发生
- **解决**: 正确做法
- **代码**: 错误 vs 正确的对比示例
- **引用规则**: 对应的 Rule #N
```

### 8.2 增加入门示例（P2 优先级）

补充 3-5 个 🌱 级别示例：
- `00-hello-world.lua` — 最小可运行程序
- `00-hello-3d.lua` — 最小 3D 场景
- `00-hello-input.lua` — 最小输入处理
- `00-hello-ui.lua` — 最小 UI 界面
- `00-hello-physics.lua` — 最小物理模拟

### 8.3 文档-API 一致性检查（P1 优先级）

设计自动化检查机制：
1. 从 .emmylua/ 提取 API 签名列表
2. 扫描 engine-docs/ 中引用的 API
3. 比对差异，输出未文档化的 API 和文档中引用的不存在 API

### 8.4 示例 manifest 标准化（P2 优先级）

为每个多文件示例添加 manifest.json，确保 AI 复制示例时不遗漏资源文件。

---

## 9. 总结

知识层是 UrhoX SCE 平台 AI 辅助开发的根基。其 **核心优势** 在于完整的 API 文档体系和高质量的示例代码（22 个，覆盖主要游戏类型）。其 **核心短板** 在于 gotcha 系统严重碎片化（1 个文件 vs 需要 12 个）、零入门示例、以及文档与引擎的一致性缺少自动保障。

**一句话**：知识层"知道的多，但组织得不够好"——信息量充足，但信息的发现性和防错性需要大幅提升。
