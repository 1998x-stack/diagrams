# Layer 6: AI 决策层 (AI Decision Layer)

> UrhoX SCE 平台七层架构分析 — 第六层

---

## 1. 定义

AI 决策层是平台的 **中枢神经系统**，负责接收用户意图、检索知识、匹配规则、选择工具、生成代码，并协调所有其他层级的运作。它的核心载体是 CLAUDE.md（及系统提示词），定义了 AI 从接收请求到交付结果的完整决策链路。

**核心隐喻**：AI 决策层是"指挥官"——它不直接搬砖（工具层做），不直接修路（运行时层做），但它决定了搬什么砖、修哪条路、用什么材料。整个平台的效率上限取决于这个"指挥官"的决策质量。

---

## 2. 设计目标

| 目标 | 说明 |
|------|------|
| **意图理解** | 准确理解用户的游戏开发需求 |
| **知识路由** | 根据任务类型定位到正确的文档和示例 |
| **规则遵从** | 严格执行 Rules #0-#14 的全部约束 |
| **工具编排** | 选择正确的工具并按正确顺序调用 |
| **质量保证** | 生成的代码符合平台最佳实践 |
| **安全守护** | 在执行过程中持续检查安全约束 |

## 3. 组成要素

### 3.1 决策流程

AI 决策层的完整决策链路：

```
用户请求
  ↓
[阶段1: 意图分析]
├── 任务类型识别（新游戏/添加功能/修复Bug/解释代码）
├── 关键实体提取（游戏类型、功能需求、错误描述）
└── 多人/单机判断（读 .project/settings.json）
  ↓
[阶段2: 知识检索]
├── 任务→文档映射（CLAUDE.md 的映射表）
├── 示例匹配（从 22 个示例中选择最相关的）
├── 脚手架选择（4 选 1）
└── API 文档查阅（按需查 engine-docs/api/）
  ↓
[阶段3: 规则检查]
├── 遍历 Rules #0-#14 的适用规则
├── 检查 gotchas（问题诊断速查表）
└── 安全约束检查（L5 横切）
  ↓
[阶段4: 代码生成]
├── 基于脚手架/示例生成代码
├── 应用规则约束（枚举、索引、路径等）
├── 添加类型标注（Rule #11）
└── 添加调试日志（首次交付）
  ↓
[阶段5: 构建验证]
├── 调用 build MCP 工具
├── 检查构建结果
└── 修复错误（如果有）→ 循环回阶段4
  ↓
[阶段6: 交付]
├── 清理调试代码（确认工作后）
└── 向用户说明代码结构和用法
```

### 3.2 任务→文档映射系统

CLAUDE.md 定义了 5 大类任务的文档检索路径：

| 任务类型 | 必读文档 | 参考文档 |
|---------|---------|---------|
| 创建新游戏 | principles.md, lua-scripting-guide.md | 脚手架, 示例 |
| 添加功能 | principles.md, api/[模块].md | recipes/, examples/api-index.md |
| NanoVG 绘图 | lua-scripting-guide.md NanoVG 节 | 01-nanovg-standalone.lua |
| 调试/修复 | lua-scripting-guide.md 关键注意事项 | 常见错误解读 |
| 多语言支持 | i18n-translation.md, i18n-resource.md | - |

### 3.3 问题诊断系统

CLAUDE.md 的"问题诊断速查"表：15+ 个 症状→解决方案 的直接映射。

```
[症状识别] → [规则定位] → [解决方案]

示例：
"NanoVG 文本不显示" → Rule #7 → "必须先 nvgCreateFont()"
"鼠标左键无响应" → Rule #12 → "用 MOUSEB_LEFT 不用数字 0"
"SetMode 不生效" → Rule #0.8 → "SetMode 已禁用，用 GetWidth()"
```

### 3.4 成功检查清单

每次交付前的自检流程：
- [ ] 调用了 build MCP 工具
- [ ] 首次交付添加了调试日志
- [ ] 代码放在 scripts/ 目录
- [ ] 基于脚手架（不从零开始）
- [ ] 如果复制示例，已做至少一轮优化

## 4. 能力边界

### 能做什么

| 能力 | 表现 |
|------|------|
| 精确的文档路由 | 根据任务类型直接定位到正确文档 |
| 规则驱动的代码生成 | 14+ 条规则确保代码质量基线 |
| 错误模式识别 | 15+ 个已知症状的快速诊断 |
| 脚手架强制 | 不允许从零开始写代码 |
| 安全意图分析 | publish 等高风险操作的意图判断 |

### 不能做什么

| 限制 | 影响 |
|------|------|
| 无反馈闭环 | 不知道生成的代码是否真正运行成功 |
| 无学习能力 | 同一个错误不能跨会话记忆 |
| 无性能意识 | 不知道生成的代码是否有性能问题 |
| 无视觉理解 | 看不到游戏运行画面，不能判断视觉效果 |
| 规则冲突时无优先级 | 两条规则矛盾时无明确裁决机制 |

## 5. 与其他层的关系

### 中枢位置

AI 决策层是整个架构的中枢，与所有层都有直接交互：

```
            L1 (Knowledge)
            ↑ 读取知识
            │
L5 (Security) ←──横切──→ L6 (AI Decision) ──遵从──→ L2 (Specification)
                              │
                              ↓ 调用工具
                         L3 (Tool Layer)
                              │
                              ↓ 触发执行
                         L4 (Runtime)
                              │
                              ↓ 产出显示
                         L7 (UI Layer)
```

### 关键交互

| 交互方向 | 关系类型 | 频率 |
|---------|---------|------|
| L6 → L1 | 知识检索 | 每次任务开始时 |
| L6 → L2 | 规则匹配 | 每次代码生成时 |
| L6 → L3 | 工具调用 | 每次操作执行时 |
| L5 → L6 | 安全约束 | 持续检查 |
| L6 → L7 | 结果呈现 | 每次任务完成时 |

## 6. 深度洞察

### 6.1 决策链路的四大断裂点

在 AI 决策层的 6 阶段流程中，存在 4 个已识别的断裂点：

#### 断裂点 1：意图分析 → 知识检索

```
用户说"做一个XXX游戏"
  ↓
AI 需要决定：
  - 2D 还是 3D？
  - 物理驱动还是纯逻辑？
  - 单机还是多人？
  ↓
但 CLAUDE.md 只有 4 个脚手架选择，覆盖不了所有游戏类型
```

**缺失**：当用户需求不完全匹配任何一个脚手架时（如"2D 物理 + NanoVG 渲染"的混合型），AI 缺少决策指导。

#### 断裂点 2：代码生成 → 构建验证（诊断真空）

已在工具层分析中详细讨论。Edit 和 build 之间没有轻量级验证。

#### 断裂点 3：构建验证 → 交付（视觉验证缺失）

```
build 成功 ≠ 游戏正确
  - 代码无语法错误 ✅
  - 但颜色可能不对 ❓
  - 位置可能不对 ❓
  - 动画可能不流畅 ❓
  - 交互可能不自然 ❓
```

AI 无法看到游戏运行画面，所以 build 成功后就认为"完成了"，但实际上可能视觉效果完全不对。

#### 断裂点 4：交付 → 下次迭代（记忆断裂）

每次会话结束后，AI 会丢失所有上下文：
- 不记得之前犯过什么错
- 不记得项目的架构决策
- 不记得用户的偏好
- 可能重复犯相同的错误

### 6.2 文档映射的"覆盖率假象"

CLAUDE.md 的"任务→文档映射"看起来覆盖了主要场景，但存在隐性盲区：

**已覆盖的任务路径**：
- 新游戏 → ✅ 明确流程
- 添加功能 → ✅ 明确流程
- NanoVG 绘图 → ✅ 明确流程
- 调试修复 → ✅ 明确流程
- 多语言 → ✅ 明确流程

**未覆盖的任务路径**：
- 性能优化 → ❌ 无任何指导
- 代码重构 → ❌ 只有">1500行要拆"
- 存档/加载 → 部分（file-storage.md），但缺少最佳实践
- 多人同步逻辑 → 部分（有示例），但缺少决策指南
- 美术风格调整 → ❌ 无指导
- 游戏平衡调整 → ❌ 无指导
- 发布前检查 → ❌ 无 checklist

### 6.3 规则执行的"遗忘曲线"

AI 在长对话中遵从规则的能力会随对话长度递减：

```
对话开始：14 条规则全部活跃
  ↓ 5 轮对话后
对话中期：核心规则（#1 build, #2 脚手架）仍活跃
          边缘规则（#4.5 unpack, #9.5 orthoSize）可能遗忘
  ↓ 15 轮对话后
对话后期：只有最强规则（#1 build）仍被记住
          其他规则依赖偶然触发（如遇到相关代码时才想起）
```

**根因**：CLAUDE.md 的规则列表是一次性注入的，在长对话中会被新信息"稀释"。

### 6.4 Skill vs Rule 的决策冲突

Skills 和 Rules 是两种不同的决策机制，但它们有时覆盖同一领域：

| 领域 | Rule | Skill | 潜在冲突 |
|------|------|-------|---------|
| 材质 | #9.6 PBRNoTexture | materials skill | Skill 更详细，Rule 更简洁 |
| 分辨率 | #0.8 GetWidth/DPR | nvg-resolution-mode skill | Skill 是 Rule 的展开版 |
| 模型导入 | (无) | import-fbx, import-glb | 无 Rule 对应 |
| 动画 | (无) | anim-info | 无 Rule 对应 |

**问题**：当 Rule 和 Skill 同时适用时，AI 应该优先遵守哪个？当前无明确规定。

### 6.5 "文档先行"原则的实际执行

CLAUDE.md 明确要求"先查文档，再写代码"，但实际执行中面临挑战：

**理想流程**：
```
收到任务 → 读文档 → 读示例 → 写代码
```

**实际流程**：
```
收到任务 → AI 凭记忆生成代码 → 遇到问题 → 补查文档 → 修改代码
```

**原因**：
1. AI 的预训练知识已包含大量 Lua/Urho3D 知识
2. 每次都读文档增加了响应时间
3. AI 倾向于先尝试再修正（"快速失败"模式）

**影响**：文档中精心记录的 gotchas 和最佳实践可能被跳过。

## 7. 风险评估

| 风险 | 等级 | 影响 | 缓解措施 |
|------|------|------|---------|
| 决策链路断裂（4 个断点） | 🔴 高 | AI 产出质量不稳定 | 逐一修复断裂点 |
| 规则遗忘曲线 | 🔴 高 | 长对话后代码质量下降 | 规则刷新机制 |
| 视觉验证缺失 | 🟡 中 | build 成功但视觉效果错误 | 截图反馈功能 |
| 文档先行原则执行弱 | 🟡 中 | gotchas 被跳过 | 任务开始时自动提取相关规则 |
| Skill/Rule 决策冲突 | 🟢 低 | 同一问题得到不一致的指导 | 明确优先级 |

## 8. 优化建议

### 8.1 决策链路断裂修复（P0/P1 优先级）

#### 断裂点 1 修复：扩展脚手架覆盖

增加混合型脚手架或脚手架组合指南：
```
scaffold-2d-nanovg-physics.lua  — NanoVG + Box2D 混合
scaffold-3d-fps.lua             — FPS 专用（MM_RELATIVE 预设）
scaffold-multiplayer.lua        — 多人游戏框架
```

#### 断裂点 2 修复：消除诊断真空

（已在工具层详细设计，见 03_tool_layer.md §8.1）

#### 断裂点 3 修复：截图反馈

在预览窗口中添加"截图插入对话"功能（已有此功能），并在 CLAUDE.md 中添加规则鼓励用户反馈截图。

#### 断裂点 4 修复：项目记忆文件

引入项目级记忆文件 `scripts/.project-memory.md`：
```markdown
# 项目记忆
## 架构决策
- 使用 NanoVG 2D 渲染（非 3D）
- 单机模式
## 已知问题
- 角色跳跃高度需要调整
## 用户偏好
- 偏好简洁代码风格
```

AI 在每次会话开始时读取此文件，减少记忆断裂。

### 8.2 规则刷新机制（P1 优先级）

在长对话中定期刷新关键规则：

```
每 5 轮对话：自动回顾与当前任务相关的规则
每 10 轮对话：完整刷新 Rules 清单
每次 build 失败：自动检索问题诊断速查表
```

### 8.3 任务路径补完（P2 优先级）

为未覆盖的任务类型添加文档映射：

```
性能优化 → [新增] engine-docs/recipes/performance.md
代码重构 → [新增] engine-docs/recipes/refactoring.md
发布前检查 → [新增] engine-docs/recipes/pre-publish-checklist.md
```

### 8.4 决策冲突解决机制（P3 优先级）

明确 Skill 和 Rule 的优先级：

```
Rule（CLAUDE.md 规则）> Skill（领域扩展）

当 Rule 和 Skill 冲突时：
1. Rule 提供的约束不可违反
2. Skill 提供的扩展信息补充 Rule
3. 如果完全冲突，以 Rule 为准
```

## 9. 总结

AI 决策层是 UrhoX SCE 平台的中枢，协调知识检索、规则执行、工具调用的完整决策链路。其 **核心优势** 在于精心设计的任务→文档映射系统、可执行的规则体系（14+ 条）、以及 publish 等高风险操作的精细意图分析。其 **核心短板** 在于决策链路的 4 个断裂点（意图→知识、代码→验证、验证→交付、交付→下次迭代）、长对话中的规则遗忘曲线、以及无法进行视觉验证。

**一句话**：AI 决策层"决策链路完整但反馈缺失"——从意图到代码的正向流程设计精良，但缺少从结果到决策的逆向反馈，导致 AI 无法自我纠正。
