# Layer 7: 用户界面层 (UI Layer)

> UrhoX SCE 平台七层架构分析 — 第七层

---

## 1. 定义

用户界面层是平台与开发者/玩家之间的 **最终接触面**，包含游戏预览、测试分发和商店展示的全部视觉交互入口。它处于七层架构的最顶层，是所有底层工作的"出口"——代码写完了要在这里看到效果，游戏做完了要通过这里发布给玩家。

**核心隐喻**：如果前六层是"厨房"（食材、菜谱、厨具、灶台、卫生、主厨），用户界面层就是"餐厅"——食客（用户/玩家）只看到这一层，体验好不好，完全取决于菜品的呈现。

---

## 2. 设计目标

| 目标 | 说明 |
|------|------|
| **即时反馈** | 代码修改后尽快看到运行效果 |
| **多端预览** | PC 和移动端都能预览游戏 |
| **发布就绪** | 从预览到发布的路径尽可能短 |
| **素材完整** | 发布时的图标、截图、宣传图一站式生成 |
| **玩家触达** | 通过 TapTap 平台直接触达玩家 |

---

## 3. 组成要素

### 3.1 开发预览

| 入口 | 形式 | 说明 |
|------|------|------|
| Preview 窗口 | Web 内嵌预览 | build 成功后通过 /workspace/dist/ 服务 |
| 截图功能 | 预览窗口右上角 | "截图插入对话"，可反馈给 AI |

**预览流程**：
```
Edit → build (MCP) → dist/ 更新 → 预览服务自动刷新 → 开发者查看
```

### 3.2 移动端测试

| 入口 | 形式 | 工具 |
|------|------|------|
| 测试二维码 | QR 码扫描 | generate_test_qrcode |
| 测试白名单 | 用户 ID 添加 | add_test_whitelist |
| 调试反馈 | 问题收集 | get_debug_feedbacks |

**测试流程**：
```
build → 配置 project.json → generate_test_qrcode → 扫码测试
                                                      ↓
                                              get_debug_feedbacks ← 测试者反馈
```

### 3.3 发布素材

| 类型 | 用途 | 生成工具 |
|------|------|---------|
| ICON | 应用图标 (512x512) | generate_game_material |
| SCREENSHOT | 商店截图 (至少 3 张) | generate_game_material |
| PROMO | 宣传图 (16:9) | generate_game_material |
| SQUARE_PROMO | 方形宣传 (1:1) | generate_game_material |
| COVER_HORIZONTAL | PC 横版封面 (460x215) | generate_game_material |
| COVER_VERTICAL | PC 竖版封面 (600x900) | generate_game_material |

### 3.4 TapTap 发布

| 步骤 | 工具 | 说明 |
|------|------|------|
| 创建开发者 | list_tap_developers | 自动创建（如不存在） |
| 配置元数据 | project.json 编辑 | 标题/类型/方向/描述 |
| 上传素材 | upload_game_material | 图标+截图+宣传图 |
| 正式发布 | publish_to_taptap | 需显式确认 |
| 绑定活动 | bind_game_jam | GameJam 报名 |
| 广告配置 | get_ad_config | 变现设置 |

### 3.5 玩家反馈回路

| 环节 | 机制 | 说明 |
|------|------|------|
| 调试反馈 | get_debug_feedbacks | 测试期用户反馈+日志+截图 |
| 评分评论 | TapTap 平台 | 发布后的玩家评价（平台外） |

---

## 4. 能力边界

### 能做什么

| 能力 | 表现 |
|------|------|
| 即时预览 | build 后自动刷新预览窗口 |
| 移动端测试 | QR 码扫描即可在手机上测试 |
| 一键发布 | 从构建到上架的完整链路 |
| 素材生成 | AI 生成图标、截图、宣传图 |
| 反馈收集 | 测试用户的错误日志和截图 |

### 不能做什么

| 限制 | 影响 |
|------|------|
| 无实时调试 | 不能在预览中设断点/看变量 |
| 无性能面板 | 不能看到 FPS、内存、渲染统计 |
| 无 A/B 测试 | 不能对比不同版本的玩家数据 |
| 无数据分析 | 不能看到留存率、漏斗等运营指标 |
| 无版本管理 | 不能回退到之前的发布版本 |
| 无热更新 | 不能不重新发布就修改线上代码 |
| 无评论管理 | 不能在平台内查看和回复玩家评论 |

## 5. 与其他层的关系

### 上游依赖

| 依赖层 | 关系 | 说明 |
|--------|------|------|
| L3 工具层 | **产出消费** | 工具产出物通过 UI 层展示给用户 |
| L4 运行时层 | **执行显示** | 运行时的游戏画面通过预览窗口显示 |
| L5 安全层 | **受保护** | dist/ 目录不可被写入 |

### 下游影响

| 影响对象 | 关系 | 说明 |
|---------|------|------|
| 开发者 | **直接用户** | 看到预览、收到反馈 |
| 玩家 | **最终用户** | 通过 TapTap 体验游戏 |
| L6 AI 决策层 | **反馈信号** | 截图插入对话、调试反馈影响 AI 决策 |

### 关键交互模式

```
L3 (Tool: build)
  ↓ 构建产物
L7 (UI: Preview)
  ↓ 开发者查看
  ↓ 截图反馈 → L6 (AI Decision) → L3 (Tool: Edit) → 循环

L3 (Tool: publish)
  ↓ 上架
L7 (UI: TapTap 商店)
  ↓ 玩家游玩
  ↓ 反馈 → L3 (Tool: get_debug_feedbacks) → L6 (AI Decision)
```

## 6. 深度洞察

### 6.1 "最后一公里"的断裂

UI 层是整个平台的"最后一公里"，但这一公里的体验并不连贯：

**预览→发布的断裂**：
```
预览成功 ────── [手动操作间隙] ──────→ 发布

中间需要：
1. 生成发行素材（ICON/SCREENSHOT/PROMO）
2. 编辑 project.json 配置
3. 上传素材
4. 调用 publish

这 4 步全部需要手动触发，无自动化流程
```

**理想状态**：
```
预览成功 → AI 提示"是否准备发布？" → 自动生成素材 → 自动配置 → 一键发布
```

### 6.2 反馈回路的不完整性

平台有两条反馈回路，都存在断裂：

**回路 A：开发者反馈**
```
代码 → build → 预览 → [开发者看到问题] → 告诉 AI → AI 修改代码
                              ↑
                       这一步是人工的，AI 看不到画面
```

**回路 B：测试者反馈**
```
发布测试 → 测试者使用 → [报告问题] → get_debug_feedbacks → AI 读取 → 修复
                              ↑
                    需要测试者主动操作
```

**缺失的回路 C：玩家运营反馈**
```
正式发布 → 玩家使用 → [数据/评论] → ❌ 无工具获取 → ❌ 无法进入 AI 决策
```

### 6.3 素材生成与发布的耦合度

`generate_game_material` 的设计将素材生成和上传紧密耦合：

```
生成素材 ──自动上传──→ TapTap 平台
                     ──同时写入──→ project.json
```

**优点**：一步到位，减少操作步骤
**风险**：无法在上传前预览/修改生成的素材

实际上 `upload_game_material` 提供了手动上传的选项，但与 `generate_game_material` 的自动上传之间缺少"先预览再上传"的标准流程指导。

### 6.4 测试工具链的薄弱

| 测试维度 | 工具支持 | 状态 |
|---------|---------|------|
| 手动测试（扫码） | ✅ generate_test_qrcode | 可用 |
| 反馈收集 | ✅ get_debug_feedbacks | 可用 |
| 自动化测试 | ❌ 无 | 缺失 |
| 性能测试 | ❌ 无 | 缺失 |
| 兼容性测试 | ❌ 无 | 缺失 |
| 回归测试 | ❌ 无 | 缺失 |

测试能力仅限于"人工扫码玩一玩 + 手动反馈"，缺少任何自动化测试手段。

### 6.5 从 IDE 到发布平台的光谱

UrhoX SCE 在 "纯 IDE" 和 "完整发布平台" 之间的定位：

```
纯 IDE ──────────────────────── UrhoX SCE ──── 完整发布平台
                                    ↑
                              当前位置
                              编码 ✅
                              构建 ✅
                              预览 ✅
                              发布 ✅
                              测试 ⚠️ 弱
                              运营 ❌ 无
                              分析 ❌ 无
```

平台在"编码→发布"段非常强，但在"测试→运营→分析"段几乎空白。

## 7. 风险评估

| 风险 | 等级 | 影响 | 缓解措施 |
|------|------|------|---------|
| 预览→发布断裂 | 🟡 中 | 发布流程繁琐 | 自动化发布向导 |
| 视觉反馈缺失 | 🟡 中 | AI 不知道画面效果 | 截图反馈标准化 |
| 测试工具薄弱 | 🟡 中 | 质量保障不足 | 基础自动化测试 |
| 运营数据空白 | 🟢 低（当前阶段） | 无法数据驱动迭代 | 长期建设 |
| 素材上传不可撤回 | 🟡 中 | 上传错误素材无法回退 | 上传确认步骤 |

## 8. 优化建议

### 8.1 发布向导（P2 优先级）

设计一个自动化的发布准备流程：

```
AI 检测到用户说"准备发布"
  ↓
自动检查 Checklist：
  □ build 是否成功？
  □ 是否有 ICON？→ 没有则提示生成
  □ 是否有 ≥3 张 SCREENSHOT？→ 没有则提示截图
  □ 是否有 PROMO？→ 没有则提示生成
  □ project.json 是否配置完整？
  ↓
全部通过 → 提示"是否确认发布？"
有缺失 → 逐项引导补全
```

### 8.2 截图反馈标准化（P1 优先级）

在 CLAUDE.md 中添加规则，鼓励 AI 主动请求视觉反馈：

```
Rule: 视觉验证
每次 build 成功后，如果修改涉及视觉效果（位置、颜色、大小、布局），
主动请求用户通过"截图插入对话"功能提供运行截图，
以验证视觉效果是否符合预期。
```

### 8.3 简易测试框架（P3 优先级）

提供基础的自动化测试支持：

```lua
-- scripts/tests/test_game.lua
local Test = require("urhox-libs/Test/Framework")

Test.describe("玩家移动", function()
    Test.it("应该在按下右键时向右移动", function()
        local player = scene_:GetChild("Player")
        local startX = player.position.x
        SimulateKeyDown(KEY_D)
        SimulateUpdate(1.0)
        Test.expect(player.position.x).toBeGreaterThan(startX)
    end)
end)
```

### 8.4 运营数据面板（P3 优先级，长期）

在 TapTap 后台集成基础运营数据查询：

```
get_app_analytics:
  - 日活 (DAU)
  - 新增用户
  - 留存率（次日/7日）
  - 评分趋势
  - 崩溃率
```

---

## 9. 总结

用户界面层是 UrhoX SCE 平台的"最后一公里"，连接开发者的代码产出和最终的玩家体验。其 **核心优势** 在于从预览到发布的完整链路（preview → QR code → TapTap）和 AI 驱动的素材生成能力。其 **核心短板** 在于预览到发布之间的手动断裂、AI 无法进行视觉验证、测试工具极其薄弱、以及完全没有运营分析能力。

**一句话**：UI 层"出口畅通但反馈不足"——代码能顺利变成可玩的游戏，但从玩家到开发者的反向信息流几乎不存在。
