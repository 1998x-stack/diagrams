# Layer 4: 运行时层 (Runtime Layer)

> UrhoX SCE 平台七层架构分析 — 第四层

---

## 1. 定义

运行时层是游戏代码实际执行的 **引擎环境**，包含 UrhoX 引擎核心、Lua 脚本虚拟机、物理引擎、渲染管线和所有底层子系统。它是唯一直接与硬件交互的层级——GPU 渲染、CPU 物理计算、输入设备采集、音频输出都在这一层完成。

**核心隐喻**：如果工具层是"双手"，运行时层就是"地面"——所有建筑（游戏）最终都要建在这块地上，地面的特性决定了建筑的可能性和限制。

---

## 2. 设计目标

| 目标 | 说明 |
|------|------|
| **跨平台一致性** | 同一份 Lua 代码在移动端、PC、Web 上行为一致 |
| **API 友好性** | Lua 绑定尽可能接近原生 C++ API，减少学习成本 |
| **性能与易用平衡** | 提供高层封装（UI 组件、ThirdPersonCamera），同时保留底层能力 |
| **渐进式渲染** | 从简单 NanoVG 2D 到完整 PBR 3D，覆盖不同复杂度需求 |
| **沙箱安全** | 游戏代码在受限环境运行，不能访问宿主系统 |

## 3. 组成要素

### 3.1 核心引擎

| 子系统 | 技术基础 | 说明 |
|--------|---------|------|
| 引擎核心 | UrhoX (基于 Urho3D 1.8) | 场景图、节点组件模型、资源管理 |
| 脚本引擎 | Lua 5.4 + tolua++ 绑定 | 游戏逻辑的唯一编程入口 |
| 坐标系 | Y-up 左手系 | 与 Unity 相同 |
| 单位 | 米 (meter) | 重力 -9.81 m/s² |

### 3.2 渲染系统

| 组件 | 用途 | 关键特性 |
|------|------|---------|
| 3D 渲染管线 | PBR 材质渲染 | 标准 PBR 工作流，内置模型 |
| NanoVG | 2D 矢量图形 | C API 完全对齐，需用 NanoVGRender 事件 |
| 精灵系统 | 2D 精灵渲染 | StaticSprite2D, AnimatedSprite2D |

### 3.3 物理系统

| 引擎 | 维度 | 典型用途 |
|------|------|---------|
| Bullet | 3D 物理 | 碰撞检测、刚体模拟 |
| Box2D | 2D 物理 | 平台跳跃、2D 碰撞 |

### 3.4 UI 系统

| 系统 | 状态 | 技术栈 |
|------|------|--------|
| urhox-libs/UI (新) | ✅ 推荐 | Yoga Flexbox + NanoVG 渲染 |
| 原生 UI (旧) | ⛔ 废弃 | Urho3D UIElement |

### 3.5 其他子系统

| 子系统 | 说明 |
|--------|------|
| 输入系统 | 键盘、鼠标、触摸，三种鼠标模式 |
| 音频系统 | 3D 空间音效，音乐播放 |
| 资源系统 | 资源缓存、热加载 |
| 文件系统 | 沙箱化读写（io 库已移除，用 File 替代） |
| 网络系统 | 多人游戏 C/S 架构 |
| 视频播放 | WASM 平台视频播放器 |

### 3.6 布局引擎

| 引擎 | 用途 |
|------|------|
| Yoga | Flexbox 布局（新 UI 系统底层） |

## 4. 能力边界

### 能做什么

| 能力 | 表现 |
|------|------|
| 2D/3D 游戏渲染 | PBR 材质、精灵、粒子、NanoVG 矢量 |
| 物理模拟 | 刚体、碰撞检测、触发器 |
| 跨平台部署 | 移动端(iOS/Android)、PC、Web(WASM) |
| 完整游戏循环 | Start → Update → PostUpdate → 事件系统 |
| 音视频播放 | 背景音乐、音效、视频播放器 |
| 多人联机 | C/S 架构、云变量、排行榜 |

### 不能做什么

| 限制 | 原因 |
|------|------|
| 无 JavaScript/TypeScript 支持 | 仅 Lua 脚本 |
| 无可视化编辑器 | 纯代码开发，无场景编辑器 |
| SetMode() 被禁用 | 分辨率由系统控制，不能程序化设置 |
| io 库被移除 | 沙箱安全，必须用 File API |
| 无着色器自定义 | 不能编写自定义 GLSL/HLSL |
| 无插件系统 | 不能加载原生 C/C++ 扩展 |

## 6. 深度洞察

### 6.1 Lua 绑定层的"翻译损耗"

UrhoX 引擎核心是 C++，通过 tolua++ 自动绑定到 Lua。这个翻译层引入了多个"损耗点"：

**eventData 的特殊访问**：
```lua
-- C++ 中直接访问成员
float dt = eventData["TimeStep"].GetFloat();

-- Lua 中需要通过 VariantMap 的方法
local dt = eventData["TimeStep"]:GetFloat()
-- 或更高效的方式
local dt = eventData:GetFloat("TimeStep")
```

这不是 bug，而是 tolua++ 绑定机制的固有特性。但对于习惯了 JavaScript/Python 的开发者来说，这是一个反直觉的陷阱。

**类型信息丢失**：
```lua
-- C++ 中编译器知道返回类型
Node* child = scene->CreateChild("Player");  // 编译器知道是 Node*

-- Lua 中类型信息依赖 .emmylua 标注
local child = scene:CreateChild("Player")  -- 运行时是 userdata
```

tolua++ 将所有 C++ 对象暴露为 Lua 的 `userdata` 类型，类型信息需要通过 EmmyLua 注解来补偿。

### 6.2 双 UI 系统的过渡期风险

当前平台处于 UI 系统过渡期：

```
旧系统 (Urho3D UIElement) ──→ 废弃但仍可用
新系统 (urhox-libs/UI)    ──→ 推荐但生态更年轻
```

**风险点**：
1. 老示例可能仍使用旧 UI 系统
2. 网上的 Urho3D 教程都使用旧 UI API
3. AI 知识库中可能存在旧 UI 用法的记忆
4. 两套系统的事件处理方式不同

**缓解措施**（已实施）：Rule #10 明确禁止旧 UI，但缺少迁移指南。

### 6.3 NanoVG 的定位模糊

NanoVG 在平台中扮演三个角色：

| 角色 | 说明 | 是否推荐 |
|------|------|---------|
| 2D 游戏渲染引擎 | 纯 NanoVG 绘制的 2D 游戏 | ✅ 推荐 |
| 自定义图形绘制 | 图表、粒子效果、特殊视觉 | ✅ 推荐 |
| UI 渲染后端 | 新 UI 系统的底层渲染 | ✅ 内部使用 |

**问题**：当开发者说"我要画 UI"时，是应该用 raw NanoVG 还是 UI 组件？Rule #8 和 #10 给出了指导，但两者的边界在实践中仍然模糊，尤其是"带交互的自定义图形"这种场景。

### 6.4 运行时的"不可观测性"

运行时层是七层架构中 **最不透明** 的一层：

| 可观测维度 | 当前能力 | 理想能力 |
|-----------|---------|---------|
| 帧率/性能 | ❌ 无 | 实时 FPS 计数器 |
| 内存使用 | ❌ 无 | 内存分配追踪 |
| 渲染调用 | ❌ 无 | Draw call 统计 |
| 物理状态 | ❌ 无 | 碰撞体可视化 |
| 脚本错误 | 部分（日志） | 带堆栈的错误弹窗 |
| 资源加载 | ❌ 无 | 资源加载耗时统计 |

开发者几乎无法知道运行时内部发生了什么，只能通过"改代码 → build → 看现象"的笨办法调试。

### 6.5 内置模型的隐性价值

引擎内置了一组基础 3D 模型（Box, Sphere, Cylinder, Cone, Torus 等），这些模型是 3D 原型开发的基石：

**已记录的尺寸信息**（engine-docs/built-in-models.md）：
- 允许 AI 精确计算物体位置和碰撞体尺寸
- 避免"先放个模型试试"的猜测式开发

**缺失的形状**：
- 半球、圆锥台、楔形等需要 CustomGeometry 手动创建
- Rule #9.5 记录了这一限制，但 CustomGeometry 的使用指南不够详细

## 7. 风险评估

| 风险 | 等级 | 影响 | 缓解措施 |
|------|------|------|---------|
| Lua 绑定陷阱导致运行时错误 | 🔴 高 | eventData 等是高频错误源 | 更完善的 gotcha 文档 |
| 双 UI 系统混用 | 🟡 中 | 渲染冲突、事件干扰 | Rule #10 + 迁移指南 |
| 运行时不可观测 | 🟡 中 | 调试效率低 | 引入性能监控组件 |
| SetMode 禁用的副作用 | 🟡 中 | 分辨率适配复杂化 | Rule #0.8 + UIScaler |
| io 库缺失的学习成本 | 🟢 低 | 标准 Lua 经验不可迁移 | 文件存储文档 |

## 8. 优化建议

### 8.1 运行时可观测性工具（P2 优先级）

提供一个内置的调试 HUD 组件：

```lua
-- 开发者在 Start() 中启用
local DebugHUD = require("urhox-libs/Debug/HUD")
DebugHUD.Enable({
    fps = true,          -- 帧率
    drawCalls = true,    -- 渲染调用数
    memory = true,       -- 内存使用
    physics = true,      -- 物理碰撞体可视化
})
```

### 8.2 UI 迁移指南（P1 优先级）

编写从旧 UI 到新 UI 的迁移对照表：

```markdown
## 旧→新 API 对照

| 旧 API | 新 API | 说明 |
|--------|--------|------|
| UIElement | UI.Panel | 容器 |
| Text | UI.Label | 文本 |
| Button | UI.Button | 按钮 |
| Slider | UI.Slider | 滑块 |
| SetSize(w, h) | width/height props | 尺寸设置 |
| SetAlignment | justifyContent/alignItems | 对齐 |
```

### 8.3 Lua 绑定差异速查卡（P1 优先级）

将 tolua++ 绑定与原生 Lua 的所有差异点整理为一张速查卡，附在 lua-scripting-guide.md 显著位置：

| C++/标准 Lua | UrhoX Lua 绑定 | 规则 |
|-------------|---------------|------|
| `obj.member` | `obj.member` 或 `obj:GetMember()` | 属性访问取决于绑定方式 |
| `map["key"]` | `eventData["Key"]:GetType()` | VariantMap 需要类型方法 |
| `io.open()` | `File:new()` | io 库被移除 |
| `array[0]` | `array[1]` | Lua 索引从 1 开始 |

### 8.4 NanoVG vs UI 决策树（P2 优先级）

```
需要在屏幕上绘制什么？
├── 按钮/菜单/表单/HUD → UI 组件（Rule #10）
├── 文字显示/字幕 → UI.Label（Rule #10）
├── 自由画布绘制（图表、自定义粒子） → NanoVG（Rule #8）
├── 整个游戏都是 2D 绘制 → NanoVG（scaffold-2d.lua）
└── 不确定 → 先查 UI 组件列表，没有对应组件再用 NanoVG
```

---

## 9. 总结

运行时层是平台的物理基础，决定了游戏能做什么和不能做什么。其 **核心优势** 在于成熟的 3D 引擎基础（Urho3D 1.8）、Lua 5.4 的现代语言特性、以及 NanoVG/Box2D/Yoga 等专业子系统的集成。其 **核心短板** 在于 tolua++ 绑定层引入的翻译损耗（eventData 等陷阱）、双 UI 系统的过渡期混乱、以及运行时的几乎完全不可观测。

**一句话**：运行时层"能力强大但黑箱运行"——引擎本身功能完善，但开发者（和 AI）很难看到内部状态，只能通过外部现象推断问题。
