# Layer 2: 规范层 (Specification Layer)

> UrhoX SCE 平台七层架构分析 — 第二层

---

## 1. 定义

规范层是平台的 **编码宪法**，定义了 AI 和开发者在编写 UrhoX Lua 游戏代码时必须遵守的全部规则、约定和最佳实践。它不是简单的编码规范文档，而是 AI 决策层（L6）的 **行为指令集**——每条规则直接影响 AI 生成代码的方式。

**核心隐喻**：如果知识层是"百科全书"，规范层就是"法律法规"——它规定了什么可以做、什么不能做、以及遇到特定情况时必须怎么做。

---

## 2. 设计目标

| 目标 | 说明 |
|------|------|
| **防错优先** | 通过规则预防已知错误，而非事后修复 |
| **决定性** | 对同一问题只给出一个明确答案，不留模糊空间 |
| **可执行** | 每条规则都有对应的代码示例（✅ 正确 / ❌ 错误） |
| **可审计** | 编号体系便于引用和追踪 |
| **渐进性** | 从基础规则（#0）到高级规则（#14），复杂度递增 |

## 3. 组成要素

### 3.1 核心规则体系 (Rules #0 - #14)

完整规则列表及分类：

#### 基础物理规则（#0 系列）

| 编号 | 名称 | 核心内容 |
|------|------|---------|
| #0 | 长度单位是米 | 所有坐标、距离单位为米，角色 ~1.8m，跳跃 ~7m/s |
| #0.5 | 坐标系 | Y-up 左手系，与 Unity 相同 |
| #0.8 | 分辨率模式 | SetMode() 禁用，用 GetWidth()/GetHeight()/GetDPR() |

#### 代码组织规则（#1 系列）

| 编号 | 名称 | 核心内容 |
|------|------|---------|
| #1 | 代码存放和依赖引用 | scripts/ 放用户代码，urhox-libs/ 只读 |
| #1.5 | 资源路径引用 | 不加 assets/ 前缀，直接从下一级开始 |

#### 开发流程规则（#2 系列）

| 编号 | 名称 | 核心内容 |
|------|------|---------|
| #2 | 脚手架起手 | 必须基于 4 个标准脚手架之一开始 |
| #2.5 | 示例可复用但需优化 | 复制示例后必须做至少一轮优化 |

#### 语言特性规则（#3-#5）

| 编号 | 名称 | 核心内容 |
|------|------|---------|
| #3 | Lua 版本特性 | Lua 5.4，eventData 特殊访问方式 |
| #4 | 数组索引从 1 开始 | 不是 0，循环用 for i = 1, n do |
| #4.5 | table.unpack 陷阱 | unpack 只在表构造器最后位置完全展开 |
| #5 | 兼容性 | 基于 Urho3D 1.8，95% API 兼容 |

#### 渲染规则（#6-#8）

| 编号 | 名称 | 核心内容 |
|------|------|---------|
| #6 | NanoVG 渲染事件 | 必须用 NanoVGRender 事件 |
| #7 | NanoVG 字体创建 | nvgCreateFont 只调用一次 |
| #7.5 | Emoji Fallback | 引擎内置，无需指定字体 |
| #8 | NanoVG 使用场景 | Canvas/图形→NanoVG；UI/HUD→UI 组件 |

#### 交互规则（#9 系列）

| 编号 | 名称 | 核心内容 |
|------|------|---------|
| #9 | 鼠标模式设置 | FPS/TPS 必须 MM_RELATIVE |
| #9.1 | 3D 模型尺寸 | 用 boundingBox 获取，不要猜 |
| #9.5 | 缺失形状 + orthoSize 因子 | CustomGeometry 替代 + 0.5 因子 |
| #9.6 | 程序化材质 Technique | 只用 PBRNoTexture 系列 |

#### 系统规则（#10-#14）

| 编号 | 名称 | 核心内容 |
|------|------|---------|
| #10 | UI 系统选择 | 废弃原生 UI，使用 urhox-libs/UI |
| #11 | 类型标注 | 未赋值变量必须 @type 标注 |
| #12 | 使用枚举值 | MOUSEB_LEFT 而非数字 0 |
| #13 | 代码模块化 | >1500 行必须拆分 |
| #13.5 | 第三人称相机 | 必须使用 ThirdPersonCamera 库 |
| #14 | 多人游戏模式判断 | 先读 settings.json 的 multiplayer.enabled |

### 3.2 脚手架约定

4 个脚手架定义了"正确的起手方式"：

| 脚手架 | 预设内容 | 开发者填充点 |
|--------|---------|------------|
| scaffold-2d.lua | NanoVG 画布、基础游戏循环 | CreateGameContent(), HandleUpdate() |
| scaffold-2d-physics.lua | Box2D 世界、物理配置 | 碰撞体定义、物理交互逻辑 |
| scaffold-3d-scene.lua | 3D 场景、自由相机、灯光 | 模型放置、材质设置 |
| scaffold-3d-character.lua | 角色控制器、第三人称相机 | 角色行为、游戏机制 |

### 3.3 Gotcha 约定

CLAUDE.md 中的"问题诊断速查表"定义了 15+ 个常见症状→解决方案的映射。

### 3.4 工作流约定

标准工作流定义：
```
选择脚手架 → 阅读文档 → 参考示例 → 编码 → build → 预览 → 调试
```

## 4. 能力边界

### 能做什么

| 能力 | 具体表现 |
|------|---------|
| 防止已知错误 | 规则 #4 防止数组索引错误，#12 防止枚举误用 |
| 统一代码风格 | 脚手架确保项目结构一致 |
| 引导正确用法 | 每条规则附带 ✅/❌ 代码对比 |
| 加速开发 | 脚手架+示例减少从零开始的工作量 |
| 避免废弃 API | #10 明确禁止原生 UI，引导新系统 |

### 不能做什么

| 限制 | 影响 |
|------|------|
| 无法覆盖所有边界情况 | 规则之外的场景靠 AI 自行判断 |
| 无自动强制执行 | 规则违反只在 build 时才可能发现 |
| 无版本演进策略 | 规则增删改缺乏变更日志 |
| 无优先级分级 | 所有规则看起来同等重要 |
| 无测试验证 | 无法自动验证代码是否遵守规则 |

## 5. 与其他层的关系

### 上游依赖

| 依赖层 | 关系 | 说明 |
|--------|------|------|
| L1 知识层 | **引用** | 规则引用知识层的具体 API 文档和示例 |
| L4 运行时层 | **约束来源** | 运行时的行为特性产生规则需求 |

### 下游被依赖

| 依赖层 | 关系 | 说明 |
|--------|------|------|
| L6 AI 决策层 | **执行** | AI 决策层严格按规则体系做编码决策 |

### 关键依赖链

```
L4 (Runtime 行为特性)
  ↓ 产生约束
L1 (Knowledge 文档记录)
  ↓ 形式化
L2 (Specification 规则定义) ──────→ L6 (AI Decision 执行规则)
```

**核心洞察**：规范层是知识层的"精华提取"——从大量文档中提炼出最关键的 do/don't 规则，供 AI 快速检索。

## 6. 深度洞察

### 6.1 规则编号体系的混乱

当前编号体系存在严重的结构性问题：

**问题 A：子编号滥用**
```
#9   → 鼠标模式
#9.1 → 3D 模型尺寸（与鼠标无关）
#9.5 → 缺失形状 + orthoSize（两个不同主题共享一个编号）
#9.6 → 程序化材质 Technique（与 #9 系列完全无关）
```

#9.x 系列本应是"交互输入"主题，实际却塞进了模型、相机、材质三个不相关主题。

**问题 B：编号不反映优先级**
- #0 是长度单位（基础但不危险）
- #6 是 NanoVG 渲染事件（标记为"极其重要"）
- #10 是 UI 系统选择（标记为"重要"）

编号大小与重要性无关，且"极其重要"标记不一致。

**问题 C：编号有间隙**
- 有 #0, #0.5, #0.8 但没有 #0.1-#0.4, #0.6-#0.7
- 编号不连续，暗示曾经有过删除或预留

### 6.2 规则密度不均衡

| 主题 | 规则数 | 实际重要性 |
|------|--------|-----------|
| NanoVG 渲染 | 4 条 (#6, #7, #7.5, #8) | 中（仅自定义图形需要） |
| 输入处理 | 1 条 (#9) + 误归类的 3 条 | 高（几乎所有游戏需要） |
| 物理系统 | 0 条（仅在 gotchas 中提及） | 高（2D/3D 物理常出错） |
| 错误处理 | 0 条 | 高（无任何错误处理指导） |
| 性能优化 | 0 条 | 中（Update 循环性能关键） |
| 状态管理 | 0 条 | 高（游戏状态是核心问题） |

NanoVG 获得了 4 条专属规则，但更常用的物理系统和错误处理却一条规则都没有。

### 6.3 脚手架设计的"填充契约"

脚手架采用"框架 + 注释占位"的设计模式，开发者通过填充特定函数来实现游戏逻辑。这是一个精巧的设计：

**优点**：
- 确保项目结构正确（场景创建、相机设置、灯光配置）
- 开发者只需关注游戏逻辑
- 不同脚手架共享相似的填充接口

**缺点**：
- 填充点之间的关系不明确（如何从 CreateGameContent 传递状态到 HandleUpdate）
- 缺少"最小填充示例"——空的脚手架无法运行，但不知道最少要填什么
- 没有验证填充结果是否正确的机制

### 6.4 规则的隐式依赖

某些规则之间存在未文档化的依赖关系：

```
#2 (脚手架) ──依赖──→ #1 (代码存放)  # 脚手架放在 scripts/ 中
#6 (NanoVG事件) ──依赖──→ #7 (字体创建)  # NanoVG 文本需要先创建字体
#10 (UI系统) ──排斥──→ #6 (NanoVG)  # UI 用 UI 组件，不要用 NanoVG
#13 (模块化) ──条件触发──→ #1 (依赖引用)  # 拆分后需要正确 require
#14 (多人判断) ──影响──→ #2 (脚手架选择)  # 多人游戏可能需要不同脚手架
```

这些依赖关系在当前文档中没有被显式说明。

### 6.5 缺失的六大规则

通过对比其他游戏开发框架的最佳实践，以下规则在当前体系中完全缺失：

| 缺失规则 | 重要性 | 说明 |
|---------|--------|------|
| **错误处理规范** | 🔴 高 | 无 pcall/xpcall 使用指导，无错误恢复策略 |
| **Update 性能规则** | 🔴 高 | 无"不要在 Update 中创建对象"等性能指导 |
| **日志规范** | 🟡 中 | 何时加日志、何时删除、日志级别选择 |
| **游戏状态管理** | 🔴 高 | 无状态机模式、无场景切换规范 |
| **模块拆分标准** | 🟡 中 | #13 说>1500行要拆，但没说按什么维度拆 |
| **触摸输入规范** | 🟡 中 | 移动端游戏缺少触摸手势处理指导 |

## 7. 风险评估

| 风险 | 等级 | 影响 | 缓解措施 |
|------|------|------|---------|
| 规则编号混乱导致 AI 误读 | 🔴 高 | AI 可能遗漏 #9.1 而执行了 #9 | 重构编号体系 |
| 密度不均导致覆盖盲区 | 🔴 高 | 物理/错误处理无规则指导 | 补充缺失规则 |
| 规则间隐式依赖 | 🟡 中 | AI 执行一条规则时遗漏相关规则 | 显式声明依赖 |
| 无优先级分级 | 🟡 中 | 规则冲突时无法判断哪条优先 | 引入 P0/P1/P2 分级 |
| 脚手架填充无验证 | 🟡 中 | 错误填充在 build 之前无法发现 | 脚手架自检机制 |

## 8. 优化建议

### 8.1 规则编号体系重构（P1 优先级）

建议采用分类前缀 + 序号的命名方式：

```
[ENV-01] 长度单位是米          （原 #0）
[ENV-02] 坐标系                （原 #0.5）
[ENV-03] 分辨率模式            （原 #0.8）

[CODE-01] 代码存放和依赖引用    （原 #1）
[CODE-02] 资源路径引用          （原 #1.5）
[CODE-03] 脚手架起手            （原 #2）
[CODE-04] 示例复用优化          （原 #2.5）
[CODE-05] 代码模块化            （原 #13）

[LUA-01] Lua 版本特性           （原 #3）
[LUA-02] 数组索引从1开始        （原 #4）
[LUA-03] table.unpack 陷阱     （原 #4.5）
[LUA-04] 类型标注               （原 #11）
[LUA-05] 使用枚举值             （原 #12）

[GFX-01] NanoVG 渲染事件        （原 #6）
[GFX-02] NanoVG 字体创建        （原 #7）
[GFX-03] NanoVG 使用场景        （原 #8）
[GFX-04] 程序化材质 Technique   （原 #9.6）

[INPUT-01] 鼠标模式设置         （原 #9）
[MODEL-01] 3D 模型尺寸          （原 #9.1）
[MODEL-02] 缺失形状             （原 #9.5 部分）
[CAM-01]   orthoSize 因子       （原 #9.5 部分）
[CAM-02]   第三人称相机         （原 #13.5）

[UI-01] UI 系统选择              （原 #10）
[NET-01] 多人游戏模式判断       （原 #14）
[COMPAT-01] 兼容性              （原 #5）
```

**优势**：
- 分类清晰，相关规则聚合
- 不再有"鼠标模式"和"材质路径"共享 #9 系列的问题
- 可独立扩展每个分类（如新增 [PERF-01] 性能规则）

### 8.2 补充六大缺失规则（P1 优先级）

参考上文 §6.5，为每条缺失规则制定具体内容。

### 8.3 规则优先级分级（P2 优先级）

为每条规则添加优先级标签：

| 级别 | 含义 | 示例 |
|------|------|------|
| 🔴 MUST | 违反必定导致错误 | #6 NanoVG 渲染事件 |
| 🟡 SHOULD | 违反可能导致问题 | #2 脚手架起手 |
| 🟢 RECOMMEND | 最佳实践建议 | #2.5 示例优化后交付 |

### 8.4 规则依赖图（P2 优先级）

在规则文档中添加"相关规则"字段：

```markdown
## Rule #6: NanoVG 渲染事件
- **相关**: #7 (字体创建), #8 (使用场景), #10 (UI 替代)
- **前置**: #0.8 (分辨率模式)
- **互斥**: #10 (UI 组件不用 NanoVG)
```

## 9. 总结

规范层是 UrhoX SCE 平台的编码宪法，其 **核心优势** 在于规则的可执行性（每条附带代码对比）和脚手架制度的强制性。其 **核心短板** 在于编号体系混乱（#9 系列包含 4 个无关主题）、密度严重不均（NanoVG 4 条 vs 物理系统 0 条）、以及 6 大关键领域完全无规则覆盖。

**一句话**：规范层"规则够用但组织不良"——个体规则质量高，但体系结构需要重构以匹配平台的复杂度增长。
