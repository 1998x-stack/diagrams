L1

Session Recall 全量历史档案

全量历史档案。无选择性地保存每次 session 的完整对话、工具调用、结果与时间戳，是其他所有层的原始数据源。 不做任何过滤或筛选。核心价值在于「记住所有发生过的事」。

底层存储结构
  • SQLite state.db + FTS5 全文搜索
  • JSONL transcripts 原始消息序列
  • 字段：session ID / 平台 / 用户 / 模型
  • system prompt 快照 + 完整消息历史
  • 工具调用链 + 工具结果 + token counts
  • 精确时间戳，支持时序查询
写入触发条件
  • 每次对话轮次自动写入，零人工干预
  • CLI / Telegram / Discord / Slack 等多平台入口
  • Signal / Matrix / WhatsApp 多渠道同步
  • 工具调用与工具结果一并写入
  • 无容量上限，所有历史永久保留
对外检索接口
  • session_search：FTS5 跨历史全文检索
  • 匹配 session 按组聚合 + 摘要生成
  • 快速模型生成 focused summary
  • 用户 recall 查询时的直接数据源
  • L2 提炼候选时的原始数据来源

L1 → L2 · Memory Gate

8 个过滤条件 — 什么内容有资格进入 L2？

从 L1 提取候选后，不是所有内容都能写入 MEMORY.md / USER.md。候选必须通过以下门槛，才能被「升格」为长期记忆。

✓ 长期有效（跨 session 可复用） ✓ 特异性（用户 / 项目 / 环境特定） ✓ 行为影响（改变未来工具选择或执行顺序） ✓ 稳定性（非临时性 session 指令） ✓ 可压缩性（能写成短句，无大段 raw data） ✓ 不与已有上下文文件重复 ✓ 通过安全扫描（无 injection / 凭证） ✓ 与已有记忆无冲突（或执行 replace） ✗ 拒绝：session 临时上下文 ✗ 拒绝：500 行日志等原始数据 dump ✗ 拒绝：API key / 密码等敏感信息 ✗ 拒绝：Prompt injection 模式
L2

Memory Learning 精选长期记忆

精选长期记忆。从 L1 历史中提炼「以后每次 session 默认应该知道的事实」，通过字符容量硬性限制确保 system prompt 不被污染。 核心价值在于「保存以后默认应该知道的事」。

MEMORY.md — 项目 / 环境 / 工作流事实
  • 容量上限 ≈ 2,200 字符
  • 环境事实（机器配置、工具路径）
  • 项目技术栈约定（pnpm, not npm）
  • 工具 quirks 和历史 workaround
  • 完成的重要任务里程碑（影响未来判断的）
  • 验证方式（先看 CI 哪个 job）
  • 代码库结构约定
USER.md — 用户画像与偏好
  • 容量上限 ≈ 1,375 字符
  • 身份、角色、技术栈水平
  • 语言偏好（中文 / 结论先行）
  • 回答风格（具体组件 vs 泛泛概括）
  • 讨厌什么（模糊高级总结）
  • 工作习惯和协作期望
  • 沟通特殊要求
五类触发来源
  • 明确请求：「以后记住…」
  • 用户纠正：Agent 做错被纠正
  • Workaround：工具失败后找到解法
  • 重复模式：多次 session 同一偏好
  • 里程碑：影响未来的已完成任务
写入操作三种
  • add：新增条目（无冲突时）
  • replace：替换冲突旧条目
  • remove：删除过期条目
  • 用 substring matching 定位旧条目
  • 写入前通过 security scanner
注入时机与生效规则
  • 下一个 session 开始时注入
  • 作为 frozen snapshot 写入 system prompt
  • 当前 session 中写入不立即生效
  • 每次 session 开始从磁盘加载
  • 容量满时需 consolidate / replace

def l1_to_l2(session, session_history): candidates = extract_candidates( messages=session.messages, tool_results=session.tool_results, user_corrections=session.corrections, final_outcome=session.answer ) for c in candidates: # ── Memory Gate: 8 filter conditions ── if not is_long_term(c): continue if not is_specific(c): continue if not affects_future_behavior(c): continue if is_ephemeral(c): continue if is_raw_data_dump(c): continue if fails_security_scan(c): continue # ── Classify: USER.md or MEMORY.md ── target = "user" if is_user_preference(c) else "memory" # ── Distill to short, stable, actionable sentence ── entry = distill(c) # ── Conflict check ── existing = find_conflicting_memory(entry) if existing: memory(action="replace", target=target, old_text=existing.unique_substring, content=entry) elif not is_duplicate(entry): memory(action="add", target=target, content=entry)
L2 → L3 · Promotion Gate

7 个升级门槛 — 从「陈述性记忆」到「程序性记忆」

单条 Memory 不会直接升级为 Skill。多条 Memory 在同一类任务中频繁共同激活，形成任务簇（task cluster），才有资格进入 Promotion Gate 评估。

✓ 多条 Memory 形成一致任务意图 ✓ 激活次数超过 MIN_ACTIVATIONS 阈值 ✓ 有明确触发语义（When to use 可以写清楚） ✓ 有稳定步骤顺序（不只是散点事实） ✓ 包含分支判断逻辑（Decision branches） ✓ 有可验证成功标准（Verification） ✓ 历史 session replay eval 通过 ✗ 拒绝：用户单点偏好（无任务流程） ✗ 拒绝：一次性任务上下文 ✗ 拒绝：过拟合到单次任务的规则 · 安装 Skill 后，原 Memory 压缩为索引条目
L3

Skill Learning 可执行工作流

可执行工作流。将多条 L2 记忆聚类成「遇到某类任务时直接执行的流程」，从陈述性记忆（我知道什么）升级为程序性记忆（我知道遇到 X 任务该怎么做）。 核心价值在于「将经验固化成可复用的因果顺序」。

SKILL.md 必要结构模块
  • When to use — 触发条件（清晰语义）
  • When not to use — 防止误触发场景
  • Context to collect — 前置需确认的上下文
  • Procedure — 有序步骤序列
  • Decision branches — 分支判断逻辑
  • Tools / Commands — 优先工具和命令模板
  • Pitfalls — 历史踩坑和纠正点
  • Verification — 任务完成标准
  • Output format — 最终汇报格式
Memory → Skill 各模块映射规则
  • 用户偏好 → Output format / Tone
  • 项目技术事实 → Prerequisites / Context
  • 工具约定 → Tools / Commands
  • 历史踩坑 → Pitfalls
  • 成功经验 → Procedure steps
  • 失败纠正 → Decision branches
  • 验证习惯 → Verification
  • 触发词 → When to use
  • 不适用场景 → When not to use
l2_to_l3_promotion.py · Promotion Gate 算法
def promote_to_skill(memory_cluster, session_history): # ── Gate 1-2: 任务意图 + 激活频率 ── if not has_coherent_task_intent(memory_cluster): return "keep_as_memory" if activation_count(memory_cluster) < MIN_ACTIVATIONS: return "wait" # ── Gate 3-4: 触发语义 + 步骤顺序 ── triggers = infer_triggers(session_history) if not triggers: return "keep_as_memory" workflow = infer_workflow(memory_cluster, session_history) if not workflow.has_ordered_steps: return "keep_as_memory" # ── Gate 5-6: 分支判断 + 验证标准 ── verification = infer_success_criteria(session_history) # ── Gate 7: replay eval 验证 ── skill_draft = synthesize_skill(triggers, workflow, verification) if not replay_eval_passes(skill_draft, session_history): return "revise_draft" # ── Promote: 安装 Skill，压缩 Memory ── skill_manage(action="create", skill=skill_draft) consolidate_memory(memory_cluster, pointer=skill_draft.name) return "promoted_to_skill"
L3 → L4 · 进入评测闭环

从「能用」到「可度量地更好」

L3 创造了 SKILL.md，L4 把它当成可优化的文本程序，在评测集上运行，通过 GEPA 的 trace-driven 反思和演化搜索，输出更优版本和 PR。

✓ Skill 使用频率高 + 用户纠正率高 ✓ 行为有明确可量化评测指标 ✓ Skill 结构完整（When / Procedure / Verification / Output 四模块齐全） ✓ eval source 可用：synthetic 或 session history · Phase 1（Skill files）已实现 ✗ Phase 2-3（tool desc / system prompt）为 planned
L4

DSPy + GEPA Self-Evolution 评测驱动文本优化

评测驱动文本优化。把 L3 Skill 等文本参数放进评测闭环，通过 trace-driven 反思和演化搜索，找到可度量更优的版本，以 PR 形式输出，走 human review。 核心价值在于「从「会做」进化到「有评测证明做得更好」」。

三类优化目标（Phase 规划）
  • Phase 1 · Skill files — 已实现
  • Phase 2 · Tool descriptions — planned
  • Phase 3 · System prompt sections — planned
  • eval source: synthetic 或 sessiondb
  • baseline metrics 对比
GEPA 反思进化机制
  • 读取完整 execution traces（非 scalar reward）
  • 诊断候选失败的具体根因
  • 生成 targeted mutation（而非随机改）
  • Pareto-aware multi-objective selection
  • 循环迭代，每轮更优
Guardrails 安全约束
  • Full test suite 必须通过
  • Skill 文件 ≤ 15KB
  • Tool description ≤ 500 chars
  • 语义不偏离原定目的
  • 所有变更走 PR review，不直接 commit
l4_gepa_evolution.py · Trace-driven 进化管线
def evolve_skill(skill_path, eval_source="synthetic"): # ── Step 1: DSPy 包装 ── module = wrap_as_dspy_module(skill_path) dataset = generate_eval_dataset(source=eval_source) baseline = evaluate(module, dataset) # ── Step 2: 收集 execution traces ── traces = collect_traces(module, dataset) # 完整执行过程，不只是分数 # ── Step 3: GEPA trace-driven 反思进化 ── candidates = GEPA.optimize( module=module, traces=traces, # error messages / reasoning logs / failures n_variants=10, mutation="reflective" # 读取 trace，诊断原因，生成 targeted mutation ) # ── Step 4: Pareto-aware 多目标选择 ── best = pareto_select(candidates, objectives=[ "task_completion", "tool_accuracy", "output_format", "no_regression" ]) # ── Step 5: Guardrails + PR ── if passes_guardrails(best, baseline): open_pr(best, metrics={"before": baseline.score, "after": best.score})
L4 → L5 · 质变

从「优化文本说明书」到「进化代码实现本身」

L4 优化的是文本参数（Skill/Prompt/Description）——「说明书」。L5 进化的是 Tool 的 Python 实现代码——「被说明书描述的系统本身」。这是从改规范到改实现的质变。

✓ Signal Collector 检测到工具代码层面的失败模式 ✓ Triage 归因：问题在代码实现而非文本配置 ✓ 可构建 reproduction script + composite fitness function · 因 AGPL 许可证以外部 CLI 调用（非 Python import） ✗ Phase 4（code evolution）为 planned ✗ Phase 5（continuous loop）为 planned
L5

Darwinian Evolver + Continuous Pipeline 代码级持续进化

代码级持续进化系统。自动发现问题、构造评测、进化工具实现代码、走 PR 流程并持续观察效果。 不是让 Agent 随便自改代码，而是「在严格评测、隔离执行、约束门禁和人类 review 下，持续提出更好的自身实现版本」。

Darwinian Evolver 进化机制（Imbue 开源）
  • Organism — 候选代码版本（Git branch / diff）
  • Population — 多候选并行演化，保留多条路线
  • Fitness — pytest + benchmark + bug repro composite score
  • Selection — fitness × novelty 加权采样（非纯 exploitation）
  • Mutation — LLM 读取 failures + learning_log 生成 targeted diff
  • Batch mutation — 一次处理多个 failure cases（类比 SGD mini-batch）
  • Mini-verify — 快速过滤无效变异（10x 效率提升）
  • Learning log — 记录历史 mutation 对 fitness 的影响
  • Crossover — 合并多个 parent 各自优势
  • Train / score split — 防过拟合，促泛化
Continuous Improvement Pipeline（L5 持续管线）
  • Signal Collector — traces / GitHub issues / CI failures / corrections
  • Triage / Attribution — 归因到 Skill / Prompt / Tool code / Policy
  • Problem Spec Generator — 目标文件 / reproduction / fitness / constraints
  • Evolution Runner — DSPy+GEPA 或 Darwinian Evolver 按需选择
  • Constraint Gate — pytest / API schema / 安全 / 权限检查
  • PR Layer — human review → merge → 继续收集 traces
  • Phase 4-5 为 planned；AGPL license 以外部 CLI 调用
darwinian_evolver.py · Population 进化核心循环
def darwinian_evolve(root_organism, train_cases, score_cases, budget): population = [(evaluate(root_organism, score_cases), root_organism)] learning_log = [] while budget.remaining(): # ── Selection: fitness × novelty ── parent = sample_by_fitness_and_novelty(population) failures = sample_failure_cases(parent, train_cases) # ── LLM targeted mutation ── child = llm_mutate( code=parent.code, failures=failures, # parent 的失败样例 learning_log=learning_log, # 历史 mutation 影响记录 constraints=problem_spec ) # ── Mini-verify: 快速过滤（10x 效率提升）── if not mini_verify(child, failures): learning_log.append({"diff": child.diff, "result": "rejected"}) continue # ── Full eval on scoring set ── child.score = full_eval(child, score_cases) population.append((child.score, child)) learning_log.append({ "diff": child.diff, "score_delta": child.score - parent.score }) # ── Select best valid + guardrails + PR ── best = select_best_valid(population) if passes_guardrails(best): open_pr(best, evidence={ "lineage": best.lineage, "tests": best.test_results, "fitness_before": root_organism.score, "fitness_after": best.score })

五层对比总结
层级 核心问题 产物 / 存储 容量约束 注入 / 生效时机 实现状态
L1 · Session Recall 记住所有发生过的事 state.db / JSONL / FTS5 无限制 不注入 system prompt ✓ 已实现
L2 · Memory Learning 以后默认知道什么 MEMORY.md / USER.md ≈ 3,575 字符总量 下个 session 冻结注入 ✓ 已实现

L5 · Darwinian Evolver 工具代码怎样自动进化 evolved tool code / PR — merge 后下个 session 生效 Phase 4-5 Planned
L4 vs L5 — 本质区别
  • L4 对象：Skill / Prompt / Tool Description（文本参数）
  • L5 对象：Tool 实现代码（可执行程序）
  • L4 变异：LLM 生成更优文本版本
  • L5 变异：LLM 基于 failures 生成代码 diff
  • L4 评测：eval cases + trace feedback
  • L5 评测：pytest + benchmark + bug reproduction
最底层逻辑公式
  • L2 Memory = compress(filter(classify(extract(L1))))
  • L3 Skill = synthesize(cluster(activated_memories))
  • L4 evolved = GEPA.select(GEPA.mutate(skill, traces))
  • L5 evolved = darwinian_evolve(code, fitness, novelty)
  • 共同原则：严格约束 + human review，不直接上线
