Trace-Driven 反思与演化搜索

GEPA 不是「让 LLM 帮我写更好的 prompt」— 它把每一次执行轨迹中的错误、反馈、评分转化为可泛化的 prompt 规则，再用演化搜索在 Pareto frontier 上保留互补候选。

反思

Trace-Driven Reflection 从执行轨迹中学习规则

不是从 reward 里估计梯度，而是从语言轨迹里抽取规则。 完整执行过程（reasoning、tool calls、outputs、errors）比稀疏标量 reward 包含多得多的学习信号 — 这是 GEPA 和 RL/GRPO 的本质区别。

四类 Trace 信号
  • 输入输出 trace — input / prediction / gold / score / feedback
  • Reasoning trace — ChainOfThought 中间推理过程
  • Tool-call trace — 工具选择 / 参数 / 输出 / 错误 / 重试
  • Schema violation trace — 枚举越界 / 格式错误 / 字段缺失
  • Multi-stage trace — 多模块管线中定位错误阶段
Reflection 的核心价值
  • 归因 — 不只知道错了，还知道哪个字段、哪个模块错了
  • 原因 — 为什么错：边界模糊、格式错、证据不足、工具失败
  • 规则 — 从局部错误抽象为可泛化的 instruction 更新
  • 定向 — 知道该改 instruction、schema 还是 retrieval
  • 本质是一种「语言梯度」
trace_example.py · 从贫瘠 score 到丰富 trace
# ── 贫瘠：只有 scalar reward ── score = 0 # 模型只知道「错了」 # ── 丰富：GEPA 看到的 trace + feedback ── trace = { "input": "充值后钻石没到账，客服也没人回", "reasoning": "用户抱怨客服无人回应 → 归为 social", "prediction": {"issue_type": "social", "needs_human": False}, "gold": {"issue_type": "payment", "needs_human": True}, } feedback = [ "issue_type wrong: '充值未到账' 是 payment fulfilment 问题", "'客服没人回' 是次要信息，不应决定 issue_type", "Rule: 充值/退款/订单未到账 → payment, needs_human=true", ]
反思七步流程
Step 1-3 · 采样与执行
  • 选择候选 — baseline 或已进化的 prompt
  • 抽 minibatch — 从 trainset 抽 3-5 条
  • 执行并记录 — 完整 trace: reasoning + outputs + scores
  • 不需要每轮看全量数据
Step 4-5 · 诊断与抽象
  • 定位失败模式 — 不是随机错，是稳定的边界问题
  • 抽象为规则 — 从「这条错了」提升为「凡是 X 场景应 Y」
  • 这一步是 GEPA 的灵魂
  • 要求 generalize from failure
Step 6-7 · 变异与验证
  • 生成 mutation — 对 predictor instruction 做定向修改
  • 测试 mutation — 在 minibatch 或 validation slice 上验证
  • 提升 → 进入 candidate pool
  • 无提升 → 丢弃或降低优先级
学习信号对比

为什么 trace 比 scalar reward 更有效？

LLM 任务里大量错误是可语言描述的：边界模糊、格式错误、工具参数遗漏。Trace 可以表达「失败原因 + 边界规则 + 修复方式」— 这是 score=0 永远做不到的。

优化方式学习信号特点
RL / GRPO标量 reward需大量 rollout，信号稀疏
Bayesian search候选分数盲搜，不知为什么错
Supervised FTinput-output pairs需修改模型权重
GEPAtrace + feedback + rule少 rollout，丰富信号，只改 prompt
搜索

Evolutionary Pareto Search 保留互补的局部赢家

如果每轮只保留平均分最高的 prompt，会丢掉覆盖不同错误模式的候选。 GEPA 用 Pareto frontier 保留「在不同 validation slice 上各有专长」的多个候选， 然后通过 mutation、crossover、merge 不断进化出更强的组合版本。

为什么需要 Pareto？
  • LLM 任务常有多种错误模式
  • 候选 A 擅长支付问题，B 擅长性能问题
  • 只看 avg 会丢掉覆盖小众但重要错误类型的候选
  • Pareto: 如果一个候选在某些目标上更好，且没被另一个全面压制，就保留
  • 每个 validation example 都是一个目标维度
搜索循环
  • Select parent — 从 Pareto frontier 选（非只选最高分）
  • Sample minibatch — 从 trainset 抽样
  • Run + collect traces — 执行并记录完整轨迹
  • Reflect + mutate — 基于 trace 的定向变异
  • Evaluate child — 在 valset 上测试
  • Update frontier — 如果互补则保留
  • Optional crossover — 合并多个候选的优势
Mutation · 定向变异
  • 不是随机编辑，是基于 trace 的反思编辑
  • 针对不同失败类型生成不同 mutation
  • 例：支付优先规则、性能 vs bug 边界、社区安全边界
  • 多个 mutation 可能各解决不同 slice
Crossover · 经验合并
  • 合并不同候选各自学到的规则
  • 风险：prompt 越变越长、规则冲突
  • 好的 merge 应压缩成层级化 instruction
  • 优先级表 > 逐条规则拼接
Component Selection
  • 多模块 program 需判断改哪个 predictor
  • query_rewrite 丢时间 → 改 rewrite prompt
  • retrieval OK 但 answer 没引用 → 改 answer prompt
  • 没有 trace 就无法做这个归因

实例

TapTap 评论 Triage 完整迭代演示

一个 ReviewTriage DSPy module，输出 sentiment / issue_type / needs_human / reason。 通过两轮 trace-driven 反思，GEPA 学到支付优先规则和性能边界规则，最终 Pareto frontier 保留三个互补候选。

迭代 1 · 支付误判
  • 输入：「充值了月卡但没到账，客服没人回」
  • 预测：issue_type=social, needs_human=false
  • 标准：issue_type=payment, needs_human=true
  • 诊断：模型过度关注「客服」，忽略「充值未到账」
  • 规则：充值/退款/订单 → payment 优先
迭代 2 · 性能边界
  • 输入：「更新后掉帧严重，打团卡成 PPT」
  • 预测：issue_type=bug
  • 标准：issue_type=performance
  • 诊断：FPS/掉帧/卡顿应归为 performance
  • 规则：lag/FPS/loading → performance; crash/broken → bug
Pareto 保留
  • 候选 A：payment override rule
  • 候选 B：performance vs bug boundary
  • 候选 C：payment + performance 组合
  • 三个都保留直到 merge 出更强版本
  • 最终以 holdout testset 验收
Metric

GEPA-Friendly Metric 成败取决于反馈质量

GEPA 的上限主要取决于 metric 的反馈质量。好的 metric 应返回：总分 + 字段级对错 + 错误原因 + 可泛化规则 + 错误模块定位。 GEPA 需要规则，不是记忆。

坏 Feedback
  • Wrong.
  • The answer is incorrect.
  • Score: 0.3
  • 对 GEPA 帮助极小
  • 模型不知道为什么错
中等 Feedback
  • issue_type wrong. Expected payment, got social.
  • 有字段级对错
  • 但缺少原因和规则
  • Reflection LM 需要猜测修复方向
好 Feedback
  • issue_type wrong: expected payment, got social.
  • 「充值后未到账」是 payment fulfilment 问题
  • 「客服没人回」是次要信息
  • Rule: 充值/退款/订单未到账 → payment, needs_human=true
  • 可直接转化为 instruction 更新

风险

失败模式 GEPA 最容易在哪里翻车

Metric 错 → 优化方向错
  • 只奖励格式合法 → prompt 格式稳但内容胡说
  • Metric 必须覆盖正确性，不只是形式
Feedback 太局部 → 过拟合
  • 「这句话应该是 payment」→ 过拟合
  • 「充值/退款/订单 → payment」→ 规则化
  • GEPA 需要规则，不是记忆
Prompt 越来越长
  • 每个失败都塞规则 → 规则垃圾桶
  • 解法：限制长度、合并规则、定期蒸馏
  • 人工 review compiled prompt
Valset 不代表真实分布
  • 支付问题过多 → prompt 过度 payment-biased
  • Valset 应覆盖真实分布 + 高价值 hard cases
Reflection LM 能力不匹配
  • 过弱 → 看不懂 trace，乱改 prompt
  • 过强 → 产生复杂但不可控的规则
  • 建议：task LM 可便宜，reflection LM 可强，compiled prompt 必须人工 review
落地

工程落地 Playbook 数据切分 · 配置 · POC 流程

数据切分（至少三份）
  • trainset — trace-driven reflection 用
  • valset — Pareto frontier 和候选选择
  • testset — 完全不参与优化，只做最终验收
  • 不要让 GEPA 看 testset
  • 起点：train 100-300 / val 50-100 / test 100-300
推荐配置
  • auto="light" — 先验证方向
  • candidate_selection="pareto" — 保留多样性
  • component_selector="round_robin" — 多模块时更稳
  • log_dir — 必须开，方便审计
  • track_stats=True — 看 mutation 和分数变化
  • 固定 seed — 方便复现
预算三档
  • light — POC，快速看收益方向
  • medium — 任务定义稳定后正式优化
  • heavy — 高价值节点，上线前优化
  • 不要一开始 heavy
  • GEPA 少样本下就可能有收益
POC 九步流程
  1. 1选任务 — 稳定 schema 的任务（review triage / RAG / 工单分类）
  2. 2做 baseline — 当前 prompt + 模型 + testset
  3. 3写 GEPA-friendly metric — score + 字段级 feedback + 可泛化规则
  4. 4跑 light GEPA — 先看 mutation 是否合理
  5. 5查看 logs — prompt 是否变好、规则是否过拟合、是否变长
  6. 6独立 testset 验收 — 只接受真实 holdout 提升
  7. 7人工 review — 检查安全、隐私、业务规则、幻觉风险
  8. 8灰度上线 — 监控错误类型、解析失败、成本、延迟
  9. 9定期 recompile — 数据分布或模型变化后重新跑
核心总结
一句话
  • Trace-driven 反思 = 把「这次为什么错」转成「下次如何避免的规则」
  • 演化搜索 = 把这些规则作为 prompt 候选不断变异、测试、保留和合并
  • 让 prompt 优化进入可评估、可追踪、可复现、可搜索的工程流程
三个上限决定因素
  • Trace 完整度 — reasoning / tool calls / errors 是否全部记录
  • Feedback 质量 — 是否包含原因 + 可泛化规则
  • Validation 代表性 — 是否覆盖真实任务分布
最适合 GEPA 的业务节点
优先级业务节点输入为什么适合
P0 评论 / 工单 Triage review → sentiment, issue_type, priority schema 清楚、feedback 容易写、规则对效果影响大
P1 RAG Grounded Answer question + docs → answer + citations 引用错误 / 证据遗漏 / 时间条件 — trace 友好
P2 UGC 风险识别 post → risk_type, severity, action false positive/negative 可解释，但需注意政策敏感性
