## 一、核心问题定义

### 1.1 研究动机

MMORPG测试是游戏开发中最高成本的环节之一，QA预算可占整体开发成本的一半以上。核心挑战：

| 挑战 | 具体表现 |
|------|---------|
| **状态空间爆炸** | 坐标、HP、背包、NPC、天气……原始状态超出LLM上下文限制 |
| **动作空间冗余** | 移动/技能/物品/对话等动作数量巨大，90%与当前任务无关 |
| **长程任务失败** | 复杂任务超过20步，传统方法卡死无法自救 |
| **Oracle缺失** | 功能性/逻辑性bug难以自动判定，需要上下文推理 |

### 1.2 现有方法的局限

```
脚本化测试    → 脆弱、维护成本高、无法适应游戏更新
DRL (Wuji)  → 需要专门训练、奖励工程、无语义理解
通用LLM Agent → 感知受限、动作选择无序、无法处理长任务
```

## 二、TITAN 核心技术框架

### 2.1 架构总览

```
┌─────────────────────────────────────────────────────────────────┐
│                     MMORPG Game Environment                     │
└───────────────────────────┬─────────────────────────────────────┘
                            │ 原始状态 + 截图
                            ▼
┌─────────────────────────────────────────────────────────────────┐
│  ① Perception Abstraction Module  (感知抽象)                    │
│     特征选择 → 离散化 → 生成精简文本状态                         │
│     RAG Database ← 游戏文档 + 专家规则                          │
└───────────────────────────┬─────────────────────────────────────┘
                            │ 抽象状态
                            ▼
┌─────────────────────────────────────────────────────────────────┐
│  ② Action Optimization Module  (动作优化)                       │
│     枚举模板 → 可行性过滤 → LLM推荐前5个动作                     │
└───────────────────────────┬─────────────────────────────────────┘
                            │ 推荐动作束
                            ▼
┌─────────────────────────────────────────────────────────────────┐
│  ③ Reflective Reasoning Module  (反射推理)  ← 核心              │
│     LLM决策 → 执行 → 进度监控 → 卡关触发反思 → 调整策略          │
│     覆盖度Map (跨轮次持久化记忆)                                  │

                            ▼
┌─────────────────────────────────────────────────────────────────┐
│  ④ Issue Diagnosis Module  (问题诊断)                           │
│     Crash Monitor | Task Status Monitor | Execution Time Monitor │
│     → 自动生成诊断报告                                           │
└─────────────────────────────────────────────────────────────────┘
```

### 2.2 模块一：感知抽象模块（Perception Abstraction Module）

**核心目的**：把高维混杂游戏状态压缩为LLM可处理的简洁符号表示。

#### 技术细节

**特征选择**（与专业测试员协作确定）：
- 玩家位置（语义区域，非原始坐标）
- 当前任务目标（从游戏日志解析）
- 玩家生命值 / 魔法值
- 附近可交互NPC / 物品
- 状态效果（buff/debuff）

**离散化方案**：
```
连续值 HP/Mana → {High, Medium, Low}  (Low: < 20%)
时间信息        → {Day, Night}（粗粒度分类）
地图坐标        → 语义区域名称
```

**可移植性设计**：
- 抽象规则以 **游戏无关模板** 实现
- 每款游戏通过 **元数据配置文件** 定义状态单元与抽象方案
- 新游戏适配时间 < 5分钟（论文实测）

**RAG集成**：
- 游戏文档向量化入库
- 每步决策前检索相关规则/知识
- 为动作推荐和反思推理提供上下文

---

### 2.3 模块二：动作优化模块（Action Optimization Module）

**核心目的**：从海量可能动作中过滤出当前最相关的~5个，避免LLM决策瘫痪。

#### 动作模板体系

```
Move(to=Location)     # 移动到指定位置
Talk(to=NPC)          # 与NPC对话
Attack(target)        # 攻击目标
Use(Item)             # 使用物品
PickUp(Item)          # 拾取物品
Explore(Direction)    # 探索方向
```

#### 双层推荐机制

**Layer 1 - 确定性规则**（专家领域知识）：
```
Rule 1: 若任务目标涉及特定NPC → 优先移动并与其交互
Rule 2: 若HP低且正在战斗     → 优先使用治疗物品或撤退
Rule 3: 若背包含任务物品      → 优先使用该物品
```

**Layer 2 - LLM启发式**（Few-shot提示）：
```
例："Given task '找隐藏洞穴' and actions [Move(N), Talk(Guard), Explore(N)],
     output the most relevant actions."
→ LLM推断 Explore(north) 比 Talk(TownGuard) 更相关
```

**验证层**：
- 所有选定动作（无论推荐与否）经语法验证脚本校验
- 无效动作自动回退到推荐列表备选项

---

### 2.4 模块三：反射推理模块（Reflective Reasoning Module）

**这是TITAN最核心的创新点**，专门解决长任务执行中的卡死问题。

#### 2.4.1 进度监控（Progress Monitoring）

**触发条件**（可配置阈值）：
```
连续 20 步 没有以下任一进展：
  - 关键任务状态推进
  - 游戏状态实质变化
  - 覆盖度多样性提升（新状态/动作发现）
```
→ 触发反思机制

#### 2.4.2 反思提示（Reflection Prompting）

触发后，TITAN暂停正常决策，向LLM发送结构化反思提示：

```
[Interactive Object]: 目标NPC在附近，但交互尝试失败。先导航到NPC坐标，再尝试交互。
[Task Progress]: 若UI未知或任务浮层开启，尝试关闭所有浮层或点击空白区域恢复可见性。
[Player]:
  (1) 若寻路成功或交互失败，尝试使用task-link或发起对话
  (2) 比较当前坐标与任务坐标，若不同先导航
[Task Requirement]: 若task link显示"ShowNpcGift"，进入对话后需要送礼
[Game Information]:
  Player Coordinates: {x, y, z}
  Nearby NPCs: {NPC1, NPC2}
  Action History: {Action1, Action2}
  Task Coverage Map: {Past Key Task1}

--- Reflection Questions ---
1. 无进展的可能原因是什么？
2. 接下来应该尝试哪些具体动作序列？
3. 这是否可能是一个bug？如果是，是什么类型，证据是什么？
```

LLM输出：分析 + 新策略计划，若强烈怀疑是bug则标记为潜在缺陷。

#### 2.4.3 执行覆盖记忆（Execution Coverage Memory）

**跨轮次持久化学习**：
```
维护抽象状态-动作转移图（State-Action Transition Graph）
  ├── 每个节点：抽象状态
  ├── 每条边：执行的动作
  └── 标注：结果（success / bug encountered）

新测试轮次：
  ├── 查询历史覆盖图
  ├── 已多次尝试无进展的路径 → 降低优先级
  └── 未探索的路径 → 提高优先级
```

效果：系统性提升跨轮次覆盖度，类似人类测试员从经验中学习。

### 2.5 模块四：问题诊断模块（Issue Diagnosis Module）

**核心目的**：自动检测并报告多类型MMORPG缺陷。

#### 三层Oracle设计

**Oracle 1 - 崩溃监控（Crash Monitor）**
```
检测：游戏客户端崩溃 / 未处理异常 / 强制终止
响应：立即记录 + 状态/动作追踪 → 生成bug报告
```

**Oracle 2 - 任务状态监控（Task Status Monitor）**
```
触发：反思模块达到上限仍无法推进
报告内容：
  ① 任务描述与目标
  ② 代理尝试的动作摘要
  ③ TITAN判断任务卡死的原因分析
  ④ 证据（抽象状态详情 + 截图）
```

**Oracle 3 - 执行时间监控（Execution Time Monitor）**
```
参考：差分测试思想（第一次执行后建立基准）
检测异常：
  - 单动作：通常 <1秒，若 >10秒 → 标记异常
  - 整体任务：通常5分钟，若 >15分钟无进展 → 标记异常
可检测：无限循环、服务器卡顿、资源泄漏
灵敏度：可调阈值（高→多检测/高误报，低→少误报/可能漏检）
```

**综合误报率：30%**（主要来源于状态抽象时的环境适配不完美）

### 2.6 核心算法流程（Algorithm 1）

```python
输入: 游戏环境G, 专家知识K, 阈值(X, Y, T), 可行性规则Φ, 测试目标O
输出: 潜在问题集I, 诊断报告R

初始化: I=∅, R=∅, 覆盖图C=加载历史, 动作历史H=∅

while 场景未终止:
    # 步骤1：感知与抽象
    raw_state = READ_STATE(G); screenshot = CAPTURE(G)
    s = STATE_ABSTRACTOR(raw_state, K)
    UPDATE_COVERAGE(C, s)

    # 步骤2：动作空间优化
    A_cand = ENUMERATE_TEMPLATES(A, s)
    A_feas = {a ∈ A_cand | Φ(a,s) = true}  # 可行性过滤
    A_rec = LLM_RECOMMEND(s, O, A_feas, C)   # LLM推荐

    # 步骤3：LLM推理与执行
    a* = LLM_DECIDE(s, O, A_rec, H)
    if not VALIDATE(a*, Φ): a* = FALLBACK(A_rec)
    o = EXECUTE(G, a*); H = H ∪ {(s, a*, o)}

    # 步骤4：监控与反思
    if NO_COVERAGE_IMPROVE(H, X) or TIMEOUT(T):
        π_refl = LLM_REFLECT(s, H, I, O)
        if BUG_SUSPECTED(π_refl):
            (ι,ρ) = MAKE_DIAGNOSIS(π_refl, s, H, I)
            I = I∪{ι}, R = R∪{ρ}
        if ESCALATION_COUNT >= Y: break
        else: INJECT_PLAN(A_rec, π_refl); continue

    # 步骤5：Oracle检测
    if CRASH_DETECTED(G):
        (ι,ρ) = REPORT_CRASH(s, H); break
    if LOGIC_ANOMALY(H) or TIME_ANOMALY(H):
        (ι,ρ) = REPORT_TO_EXPERT(s, H, K)
    if TASK_COMPLETE(G, O): break

return (I, R)
```

### 3.3 RQ1：任务完成率与状态覆盖度

| 方法 | 任务成功率 | 平均状态覆盖度 |

- ReAct常在任务早期卡死，Wuji因训练时间限制偶尔不收敛

#### Bug类型分布

| Bug类型 | TITAN | ReAct | Wuji | Human |

- **Human误漏**：人类测试员专注完成任务，逻辑异常常被忽略

## 四、发现的新型Bug

### 4.1 Model Logic Bug（几何穿模）
**现象**：角色可穿透世界几何体（墙壁/地板）进入未渲染区域
**根因**：缺失资产导致碰撞数据未加载
**为何TITAN独家发现**：非线性路径探索 + 愿意尝试非预期交互
**其他方法**：Wuji/ReAct/Human均只走预期路径，从未触碰边界异常

### 4.2 Hang Interaction Bug（交互挂起）
**现象**：使用物品的两种途径（屏幕UI按钮 vs. 背包菜单）之一触发游戏挂起
**根因**：冗余但有缺陷的UI路径中未处理的状态转换
**为何TITAN独家发现**：整体感知模块识别所有可交互元素，LLM动作生成不固定于单一最优路径
**Wuji**：总是选择背包菜单，永远触发不了挂起路径

### 4.3 Step Counting Bug（步数计数错误）
**现象**：任务要求击杀6个NPC，击杀5个后任务被标记为完成
**根因**：任务状态机中的差一错误（off-by-one）
**为何TITAN独家发现**：中断驱动的非线性行为（战斗中暂停去采集资源节点）创造了特定执行序列，暴露了错误的完成条件
**Human**：按顺序击杀6个目标，观察到正确行为，未发现不一致

## 五、技术创新总结

### 5.1 与现有方法的本质区别

```
                    训练需求   语义理解   长任务   跨游戏   Bug类型
脚本化测试            无         无        弱       差       有限
DRL (Wuji)           大量        无        弱       差       Crash
ReAct (通用LLM)       无         有        弱       中       Crash/部分Hang
TITAN                 无        强         强       好       Crash+Hang+Logic ✓
```

### 5.2 关键设计原则

1. **零训练**：利用LLM零样本推理能力，无需游戏特定训练
2. **人类专家知识注入**：RAG + 规则 = 领域知识与LLM推理的结合
3. **自适应性**：反思+覆盖记忆 = 动态调整策略
4. **结构化Oracle**：不依赖简单崩溃检测，构建多层诊断体系
5. **工程化实用性**：已在8个商业游戏QA流水线部署

### 5.3 局限性

- **误报率30%**：主要来源于状态抽象的环境适配不完美
- **模型依赖**：目前仅测试GPT-4o，其他模型表现未知
- **游戏类型限制**：对依赖反射操作或叙事极简的游戏类型优势减弱
- **实验规模**：仅在2款游戏20个任务上验证

---

## 六、对自动化测试领域的启示

1. **任务完成率是工业落地的前提**：Bug检测能力再强，若代理频繁卡死，无法融入高风险生产流水线
2. **零训练框架的价值**：频繁迭代的游戏（每天数百次代码变更）需要无需重训即可适应的测试方案
3. **覆盖度 vs. 完成率需要平衡**：纯完成率（Human 100%）覆盖度仅33%，纯探索可能完成率低
4. **LLM反思机制是长任务的关键**：消融实验明确证明反射推理对复杂任务不可或缺
5. **多样化交互策略暴露更多Bug**：单一策略代理系统性错过特定路径上的缺陷
