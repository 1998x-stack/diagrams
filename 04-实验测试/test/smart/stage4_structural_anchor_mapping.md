# 阶段四：结构锚点映射（Structural Anchor Mapping）

## 概述

结构锚点映射是 SMART 框架中最具创新性的阶段，负责建立**高层子目标与底层代码变更之间的上下文感知关联**。它回答了一个关键问题：*在多步骤任务的哪个阶段，测试哪些代码变更才是有意义的？*

---

## 核心目标

> 构建一个映射函数 $M: C \to \mathcal{P}(S)$，将每个结构锚点 $c_i \in C$ 分配到一个或多个子目标子集，表明该锚点在哪些游戏阶段"可达且语义相关"。

---

## 为什么需要上下文感知映射？

在多步骤任务中，**相关代码会随玩家进度动态变化**。

**反例**：若没有上下文映射，在"烤箱烘烤"子目标之前，智能体可能反复与烤箱交互，但此时生披萨尚未存在，代码中的烤箱逻辑永远无法被正确触发。

**示例**：切番茄完成（子目标 1）后，"整个番茄与砧板交互"的代码逻辑在后续正常游玩中永远不会再被触发。对这段代码的测试只在子目标 1 期间有意义。

---

## 形式化定义

**定义 1（结构锚点映射）：**

设：
- $S = \{sg_1, sg_2, \dots, sg_n\}$：Stage 2 输出的有序子目标集合
- $C_L$：修改行集合（Stage 1）
- $C_B$：修改分支集合（Stage 1）
- $C = C_L \cup C_B$：全体结构锚点集合

映射函数为：

$$M: C \to \mathcal{P}(S)$$

其中 $\mathcal{P}(S)$ 为 $S$ 的幂集。

**约束条件：**
- **完备性**：对每个锚点 $c_i$，其映射集 $M(c_i) \neq \emptyset$（每个锚点至少关联一个子目标）
- **多对多**：一个锚点可关联多个子目标（$|M(c_i)| \geq 1$）

---

## 两阶段混合构建方法

### 阶段一：静态分析（粗粒度可达性分析）

**目标**：建立保守的可达性关系（过近似）

**方法**：
1. 识别每个子目标在代码中的**主要入口点**（primary entry point）
2. 从这些入口点出发，向后追踪**调用图**（call graph）和**数据依赖关系**
3. 识别所有潜在可达的结构锚点候选集

**特点**：
- 结果是保守的**过近似**（over-approximation）——可能包含技术上可达但语义不相关的锚点
- 效率高，为第二阶段提供筛选范围

---

### 阶段二：LLM 语义过滤（细粒度语义相关性判断）

**目标**：从候选集中剪除语义不相关的锚点

**方法**：

对每个子目标 $sg_j$ 及其候选锚点集中的每个锚点 $c_i$：
- 向 LLM 提供 $sg_j$ 的描述 + $c_i$ 的代码片段
- LLM 判断：该锚点是否在**语义和逻辑上**与完成 $sg_j$ 直接相关？
- 若不相关，则从映射中剪除

**特点**：
- 利用 LLM 对游戏逻辑的理解能力
- 将"技术可达"过滤为"真正需要测试"

---

## 动机示例（Onion Pizza Quest）

**代码变更（结构锚点）：**

| 锚点 | 描述 |
|------|------|
| $c_1$ | 判断柜台上面团是否已放置有效番茄+奶酪组合的逻辑 |
| $c_2$ | 切碎番茄和洋葱的状态转变逻辑 |
| $c_3$ | 烤箱内生披萨变为熟披萨的状态转变逻辑 |

**映射结果：**

```
M(c1) = {sg3}  → "组装生披萨"阶段才相关
M(c2) = {sg1}  → "切番茄/洋葱"阶段才相关
M(c3) = {sg4}  → "烤箱烘烤"阶段才相关
```

**对比无映射的情况：**

| 情况 | 问题 |
|------|------|
| 无映射 | 智能体在任何时间都可能尝试与烤箱交互或放置洋葱，但此时条件不具备，大量探索无效 |
| 有映射 | 智能体只在对应子目标阶段才会收到探索相关代码的激励，探索高效且精准 |

---

## 与 Stage 5 的衔接

映射结果 $M$ 在 Stage 5 的自适应混合奖励中起到"上下文感知门控"的作用：

```
当前子目标索引 j
       ↓
检查当前触发的锚点 c ∈ C_step
       ↓
仅当 sgj ∈ M(c) 时，才给予结构性奖励
```

这确保了：
- **结构奖励不会在错误的时间点触发**
- **防止智能体在早期阶段就"提前消耗"后期才可达的代码覆盖奖励**

## 关键价值

| 价值维度 | 说明 |
|----------|------|
| **精准性** | 只在正确时机测试正确代码，避免无效探索 |
| **可达性保证** | 确保深层代码逻辑在其可达的游戏阶段才被激励探索 |
| **上下文感知** | 理解多步任务的动态依赖关系，而非静态全局视图 |
| **防止奖励误导** | 避免智能体因全局化的结构奖励而陷入无意义的代码触发行为 |

---

## 局限性（论文 4.4 节）

> **AST 静态分析的局限**：对于使用反射（reflection）、动态资源加载或热交换脚本（如 Lua/Python）的游戏引擎，静态 AST 分析无法完全解析运行时的控制流。若代码更新大量依赖动态调度机制，Stage 4 的锚点映射可能无法识别或正确关联这些代码路径。
>
> **缓解方向**：引入动态调用图生成（dynamic call-graph generation）作为静态 AST 差分的补充。
