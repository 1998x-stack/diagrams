系统概览
WHAT

GEPA 是什么

GEPA (Genetic Extraction of Prompt Actions) 是 DSPy 框架中的进化式 prompt 优化器。 它通过 reflection model 分析训练集上的错误，自动生成 prompt mutation 候选， 并通过 Pareto 搜索保留互补性最强的候选，最终产出优化后的 system prompt。

核心思想
  • 不构造"完美回答"，构造"失败切片"
  • 从真实会话中提取 Agent 犯错的因果链
  • 让 GEPA 自动发现通用防错规则
技术栈
  • DSPy — Prompt 程序化框架
  • DashScope Qwen — 基础 LM + Reflection
  • Claude Code — 失败切片提取 Agent
  • FastAPI — 可视化平台

SKILL

失败切片提取工作流

Agent 接收一个 session hash，深度分析 .traj 轨迹文件，通过 8 条多路召回规则搜索失败候选， 再通过 因果链追溯 确认根因，最终输出结构化的失败切片和 GEPA 训练样本。

1

概览会话结构

读取 session 元数据（头部 ~50 行），grep "role": "user" 定位所有用户 turn， grep "is_error": true 定位错误步骤。不全量读取 .traj（通常 1-3 MB）。

2

多路召回 Failure Candidates

8 条规则并行搜索——构建失败、工具错误、用户纠正、已读证据未用、大量写入后崩溃、 状态漂移、缺失验证、重复操作。宁多勿漏，后续过滤。

3

深度调查每个 Candidate

按 ±400 行窗口读取 .traj，构建因果链：evidence_turn → failure_turn → fix_turn。 回溯到第一个与 tool evidence 矛盾的假设作为根因。

4

写入 _slices.jsonl

每个 slice 对应一个失败点，包含 target_module（7 枚举）、failure_type（8 枚举）、 证据链、feedback（中文）和 general_rules（英文）。

5

写入 _gepa.jsonl

将每个 slice 转为 GEPA 训练样本，包含 4 个 input 字段（summary, timeline, events, evidence） 和 3 个 gold 字段（issue_frame, next_action, should_verify）。

GEPA 进化优化算法
ALGO

DSPy GEPA 如何迭代

GEPA 类似遗传编程：每轮迭代从当前最优候选中选择一个"父代"， 通过 reflection model 分析其在训练子集上的失败模式，生成改进后的"子代" prompt。 子代在 val 集上评估，优于父代则加入候选池，最终通过 Pareto 前沿选择最佳程序。

1

Baseline 评估

零样本 ChainOfThought 在 valset（19 examples）上评估。 无任何领域知识的 baseline prompt 得分 0.489。

2

Reflection（反思）

从 trainset 随机抽取 3 个 examples，用当前 prompt 预测， 与 gold label 对比。Reflection LM 分析失败原因， 并生成 prompt mutation 建议。

3

Mutation（变异）

将 reflection 建议融入父代 prompt，生成子代。 变异类型：添加领域知识、修正规则、强化约束、 调整角色定位等。每轮产出 0-1 个新候选。

4

Evaluation + Pareto

子代在 valset 上评估（19 tasks × 1 score each）。 计算平均分，更新 Pareto 前沿—— 保留在任何 task 上是"最优"的候选，确保互补性。

GEPA 学到的规则
RULES

优化后的防错规范 prog_28 提炼

GEPA 从 90 个失败样本中自动提炼出 8 条通用防错规则， 可直接注入 CLAUDE.md 或 Agent system prompt，降低编码 Agent 的犯错率。

1
API 验证前置 — 在写任何调用自定义库（UI框架、音频、特效、NanoVG）的代码之前， 必须先 grep 代码库确认方法名、参数顺序和返回值类型。源代码是唯一的 API 文档。
2
Build ≠ 正确 — 构建成功不代表运行时正确。nil 引用、类型不匹配、参数缺失在构建阶段都检测不到。 但 build 对结构完整性仍有意义：确认 Start() 存在、require 正确、语法无误。
3
Tool evidence > 直觉 — 工具返回的结果（Read/Grep/Build 输出）是 ground truth。 不要用"常识"或记忆中的 API 知识覆盖工具证据。
4
复制时复制依赖 — 从一个文件复制实现逻辑到另一个文件时，必须同时复制所有 require 语句和模块导入。 不要假设全局可用。
5
工具参数完整性 — 调用外部工具（build、Task、CloudSave）前，检查所有必填参数。 参考项目配置文件或代码库中的成功调用示例。
6
Lua 作用域纪律 — local 函数必须在引用之前声明，Lua 没有 hoisting。 新建模块时确认 entry-point 函数（Start()/init()）存在且导出正确。
7
UI 隐藏态安全 — overlay/全屏组件隐藏时必须处理 pointer-event 拦截。 SetStyle({width=nil}) 不会重置属性 — 使用显式值。
8
小步验证 — 结构性变更（新文件、入口点修改、init.lua 改动）后立即 build 确认结构完整性。 每次不超过 2-3 个编辑再验证。

结论与改进路径

关键发现
  • Light 已捕获 ~92% 信号：Heavy 额外 40 分钟仅贡献 +1.05pp
  • 瓶颈在数据质量：4 个顽固任务占 val 21%，所有候选无法突破
  • 角色定位决定性能："debugging assistant" 远优于 "analyst"
  • 规则自行涌现：GEPA 发现了 3 条人工未标注的 Lua 特定规则
改进路径
  • P0 — 修正 4 个顽固任务 gold label（+2-4pp）

  • P1 — 归一化 issue_frame 到 6 类
